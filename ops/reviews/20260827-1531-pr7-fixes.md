## Finding 1 (P1) — `sdk/src/journal-client.ts:193`: make effect election atomic with the provider call

**The hole.** `effect.record` was a one-phase election. A worker that died
after the journal returned `deduped: false` and before it called its provider
left a winner nobody performed; every retry then read `deduped: true` and
skipped the call, so the run completed with the declared effect never having
happened. `kernel/DESIGN.md` §1.9 documented this honestly as "at-most-once,
not exactly-once" — which is a fail-open against Appendix A rule 5, not a
design decision, so it is now closed rather than described.

**The fix — two phases, elect → perform → confirm.** An election is a claim on
the provider call; only a *confirmed* election proves the call happened. An
election left unconfirmed is reclaimed by the next attempt, so the effect still
occurs exactly once rather than never. Reclaim is safe by construction: the
kernel admits `effect.record` only from the attempt that holds the lease, and
one attempt holds it at a time, so a *later* attempt reclaiming means the
holder is dead. A holder re-recording its own unconfirmed election still reads
`deduped: true` — it is alive and already owes the call.

**Residual, stated plainly.** A worker that dies *after* the provider call and
*before* confirming leaves the election reclaimable, so the next attempt calls
the provider a second time. That window cannot be closed by a second record —
it needs the mount to be the writer (gate 4), which `DESIGN.md` §1.9 now says.

strictly worse than the one that remains (effect happens twice, journaled), and
this is the same trade every at-least-once boundary makes.

## Finding 2 (P1) — `kernel/relayflowd-core/src/state.rs:278`: preserve pins omitted by intermediate agent steps

**The hole.** `self.current_pins = payload.end_pins.clone()` replaced the run's
whole pin chain with each agent completion's end pins. Agent A pins `repo`;
agent B declares only `mount`; B's completion dropped A's `repo` revision, so a
later step declaring `repo` sourced it from a worker as if the run had never
pinned it — against Appendix A rule 6, where the next step's start *is* the
previous end state.

**The fix.** The chain merges **per surface**. A step declares only its own
surfaces (rule 1), so its `end_pins` speak for those alone; every other surface
the chain holds is untouched by it and survives.

| file:line | change |
|---|---|
| `kernel/relayflowd-core/src/state.rs:278-281` | `self.current_pins = pins::chain_forward(self.current_pins.take(), payload.end_pins.clone())` |
| `kernel/relayflowd-core/src/state/pins.rs:106-141` | `chain_forward` — per-surface merge for workspace and streams; a completion with no end pins leaves the chain as it was |

## Finding 3 (P1) — `kernel/relayflowd/src/server/session.rs:394`: compare worker pin values before dispatching

**The hole.** `worker_holds` compared only surface *names*. If the worker that
`starting_pins` elected detached before `dispatch` and a replacement advertised
the same surfaces at different revisions or offsets, the attempt was dispatched
against pins the new worker does not stand at — its journaled starting state
did not describe the worker that received it.

**The fix.** Two parts, because a name-only check was not the whole story:

1. **Compare the values.** `pin_value_mismatch` requires the selected worker's
   reported revision/offset to equal the attempt's pin, *unless* the dispatch
   is itself the instruction to move there — a `reset` retry carrying
   `restore_pins` equal to the pins (Appendix A rule 4), where the worker's
   current revision is irrelevant because it is being told to restore.
2. **Keep the hub's view of each worker current.** A worker's attach-time pins
   are only true until it changes them. `advance_worker_pins` merges a
   completion's `end_pins` into the completing connection's reported state
   *before* that completion drives the run, so a chained pin is checked against
   what the worker actually holds rather than a stale snapshot. Without this,
   value comparison would false-positive on every legitimate chain carry.

A mismatch is a **typed, journaled decision**, not a silent decline: `dispatch`
returns `DispatchOutcome::PinMismatch` and the drive loop journals a declared
`worker_error` completion through the normal completion path, so retry policy
and the failure taxonomy hold and the step re-elects. The previous behavior
(decline, park, let the lease expire unexplained) is gone.

|---|---|
| `kernel/relayflowd/src/worker.rs:21-37` | `DispatchOutcome { Dispatched, NoWorker, PinMismatch { detail } }`; `dispatch` returns it instead of `bool` |
| `kernel/relayflowd/src/server/session.rs:402-404` | the value check, at the dispatch boundary |
| `kernel/relayflowd/src/server/session/matching.rs` (new, 80 lines) | `select_worker`, `worker_holds`, `pin_value_mismatch` — carved out of `session.rs`, which the change pushed past 500 lines |
| `kernel/relayflowd/src/server/session.rs:122-158` | `advance_worker_pins` |
| `kernel/relayflowd/src/server.rs:258-266` | `step.complete` advances the worker's reported pins before driving |
| `kernel/relayflowd/src/engine/drive.rs:113-135` | `PinMismatch` → journal and re-drive |
| `kernel/relayflowd/src/engine/drive.rs:146-176` | `fail_dispatch_closed` — a declared `worker_error` naming both revisions |

## Finding 4 (P2) — `kernel/relayflowd/src/server/client.rs:68`: keep CLI resume waiting while the lease remains active

**The hole.** A fixed `Instant::now() + 30s` deadline. Any agent attempt longer
than 30 seconds made `relayflowd resume` die with a raw error while the worker
was still heartbeating and the run was perfectly healthy.

**The fix.** The wait follows the **lease**, not a wall-clock limit of the
CLI's own. Every poll is one decision over the registry row the server already
maintains (`step.heartbeat` persists the renewed deadline into
`next_wake_at_ms`): keep waiting while the heartbeat-renewed lease is live, stop
when the run reaches a terminal state or leaves `waiting_worker`, and fail
closed with a declared reason only when the lease genuinely expires (plus a
5s grace for the reconciler's sweep). A `waiting_worker` row with no deadline
records no live lease and also fails closed, rather than hanging on nothing.

| file:line | change |
|---|---|
| `kernel/relayflowd/src/server/client.rs:14-18` | `LEASE_SWEEP_GRACE_MS` |
| `kernel/relayflowd/src/server/client.rs:20-53` | `ResumeWait` + `resume_wait(status, lease_deadline_ms, now_ms)` — the whole give-up policy as one pure decision |
| `kernel/relayflowd/src/server/client.rs:106-133` | `wait_for_out_of_band_completion` — the loop, with the fixed 30s deadline removed |

**Test** — `kernel/relayflowd/src/server/client.rs`,
`resume_waits_while_the_heartbeat_renewed_lease_is_live`: ten minutes into an
attempt — twenty times the old fixed deadline — with a lease renewed 30s out,
the verdict is `KeepWaiting`; it stays `KeepWaiting` up to the deadline plus
the sweep grace and becomes `LeaseExpired` only past it; terminal and
non-waiting states answer immediately.

**Mutation check** — reintroduced the reviewed defect (a fixed 30s cap that
ignores the live lease):

```
test server::client::tests::resume_waits_while_the_heartbeat_renewed_lease_is_live ... FAILED
assertion `left == right` failed
  left: LeaseExpired
 right: KeepWaiting
test result: FAILED. 0 passed; 1 failed; 0 ignored; 0 measured; 17 filtered out
```

**Stated honestly:** the pin is a unit test on the extracted decision, not a
>30s integration test. Proving "waits past 30 seconds" end-to-end costs 30+
seconds of suite time for no additional information — the decision function
*is* the give-up policy, and the mutation above is exactly the defect that was
reported. The pre-existing regression
`resume_without_a_worker_parks_immediately_instead_of_timing_out` still pins the
other half (a run with no worker must not wait at all).
