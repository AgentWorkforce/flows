### ADVISORY-1: event.rs dedupe_key function has off-by-one error in replace_range

**Location:** kernel/relayflowd-core/src/event.rs:58

**Finding:**
The `replace_range` call reads:
```rust
output.replace_range(start..start + 10 + end + 2, &rendered);
```

This calculates the range as `[start, start+10+end+2)`, which is `[start, start+12+end)` for `{{payload.X}}` where `X` has `end` bytes.

The actual template syntax is `{{payload.` (10 chars) + `path` (end chars) + `}}` (2 chars) = 12 + end chars total.

So the range `start..(start+10+end+2)` = `start..(start+12+end)` is correct.

**Wait—retracting this finding.** On closer inspection:
- `start` is the index of `{{payload.`
- We skip the first 10 characters to get to the path: `&output[start + 10..]`
- In that substring, `end` is the position of `}}`
- So the full token length is 10 (for `{{payload.`) + end (path length in the substring) + 2 (for `}}`)
- Total: `start + 10 + end + 2`

The code is correct. **WITHDRAWN.**

### ADVISORY-2: TriggerSpec validation requires event_type and dedupe_key_template to both be present or both absent, but does not explain why in comments

**Location:** kernel/relayflowd-core/src/spec.rs:89

**Finding:**
Line 89 validates:
```rust
|| trigger.event_type.is_some() != trigger.dedupe_key_template.is_some()
```

This enforces that `event_type` and `dedupe_key_template` must both be present or both absent (XOR not allowed). This is a logical constraint, but it's not documented in comments or in the TriggerSpec struct definition.

**Why ADVISORY:**
The code is correct. The lack of a comment explaining the invariant makes the code harder to maintain. A future developer adding fields might not understand why this constraint exists.

**Recommendation:**
Add a comment at spec.rs:353-362 (TriggerSpec definition) explaining: "For event-triggered flows, event_type and dedupe_key_template must both be present. For non-event triggers (e.g., cron), both must be absent. This is enforced in validation."

### ADVISORY-3: NEXT.md claims kernel tests prove idempotency, but the test name doesn't match the claim

**Location:**

- kernel/relayflowd/tests/event_wake.rs:6 test is named `matching_event_wakes_once_with_fresh_context`

**Finding:**
The test at lines 47-49 submits the event twice and asserts `second.matched && second.deduped` and `second.run.is_none()`. This correctly proves idempotency.

However, the test name emphasizes "fresh_context" rather than "dedupe" or "idempotency", which makes it harder to find when searching for the idempotency proof.

**Why ADVISORY:**
The test is correct and does prove the requirement. The name is merely suboptimal for discoverability.

**Recommendation:**
Consider renaming to `event_dedupe_prevents_double_execution` or `matching_event_executes_once_per_dedupe_key`.
