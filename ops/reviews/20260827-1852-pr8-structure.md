## 1. The kernel boundary — small and pure (AGENTS.md rule 2; RFC §4)

The central structural question is whether `cli` and `triggers` on `RunSpec` smuggle product logic into the kernel. They do not.

- **Imports prove it.** `spec.rs:14-18` pulls only `std::collections::{BTreeMap, BTreeSet}`, `serde`, `serde_json::Value`, `thiserror::Error`. No `std::fs`, no `std::process::Command`, no `tokio`, no `reqwest`, no provider SDK. The `Command`/`CommandSpec` symbols in the file are a **data enum** for the deterministic step's `command` field, not process spawning. The kernel never resolves a binary, never runs `auth status`, never matches a trigger.
- **Carried, not executed.** `spec.rs:76-82` — `cli: Option<String>` annotated *"Preflight resolves step → flow → project config before the kernel is asked to start a run"*; `triggers: Vec<TriggerSpec>` annotated *"Inert gate-1 declarations. Matching and dispatch belong to gate 2."* This mirrors how the kernel already carries `budget` (journaled, not computed) and `recovery_mode` (policy, not executed). `TriggerSpec` (`spec.rs:335-340`) is `#[serde(deny_unknown_fields)]` with just `id` + `executor` — two strings, nothing executable.
- **Shape validation only.** `RunSpec::validate()` (`spec.rs:88-118`) adds: empty flow-cli → `EmptyCli`; trigger with empty id/executor → `InvalidTrigger`; duplicate id → `DuplicateTrigger`; empty step-cli → `EmptyStepCli`. This is the same class of structural check the kernel already performs for step ids, duplicate steps, and zero iterations — it guards the integrity of data it carries, it does not interpret it. `deny_unknown_fields` means a guessed `worker` field is rejected, not silently dropped.

**No new primitive.** `cli` is a field on two *existing* step kinds (`Llm`, `Agent`) — `spec.rs:240-243, 247-248` — not a new step verb. `TriggerSpec` is inert data feeding the existing `on` resident verb. RFC settled decision #13 pins the kernel vocabulary as three step verbs (`run`/`llm`/`agent`) + four resident verbs (`on`/`human`/`dispatch`/`done`); this PR adds nothing to that set. Preflight is an SDK **helper**, not a kernel primitive — "helpers over primitives" held.

**`completionReason` discipline is strengthened, not weakened.** `machine/tests.rs:65-108` (`every_failed_run_terminates_with_declared_completion_reasons`) iterates every failure kind (VerificationFailed, RetriesExhausted, LeaseExpired, Crashed, Timeout, WorkerError, BudgetExceeded, Canceled) and pins two things: (a) the failed attempt appends a typed `StepCompletedPayload` whose `completion_reason` equals the declared enum, and (b) the run terminates in its journal with `RunCompletionReason::StepFailed`. This is exactly the RFC §1 / AGENTS.md rule 4 gate made testable. No failure path leaks a raw error.

**fail-closed.** `spec/tests.rs:119-138` (`preflight_data_is_fail_closed`) pins that a trigger with a guessed `worker` key is rejected by `deny_unknown_fields`, and an empty step `cli` yields `EmptyStepCli`. No silent acceptance.

## 2. The SDK side — single-purpose, I/O at the edges

**`preflight.ts` (221, new)** — pure predicates. The load-bearing line is `preflight.ts:26`: *"Environment facts are injected; this module performs no I/O."* All environment access sits behind the `PreflightProbes` interface (`cli` / `executor` / `command`), so the predicates are testable against a simulated environment — the SDK-side analogue of the kernel's "built against a simulated clock" rule. Probe exceptions are caught and mapped to a declared kind (`probe_failed`); each deterministic step leaves exactly one declared warning (`unprovable_effects` / `command_unresolved` / `command_unprovable`) — covenant 2's "refuses *or* warns, never silent," with the comment at `preflight.ts:153-160` explaining *why* a deterministic command is warned rather than refused (it runs as `/bin/sh -c`, so an unresolved first word may still be a shell builtin). Clean, single-purpose, no dead code.

**`failure-kinds.ts` (43, new)** — the closed refusal/warning taxonomy as `as const` arrays with derived union types and an `isCheckFailureKind` guard. The closed failure set (RFC covenant 2) made structural and tiny. Single purpose.

**`cli.ts` (246, new)** — the `flows check` I/O composition root, and the *only* place real I/O lives. It injects concrete `systemProbes` (`spawnSync`/`which`/`accessSync`) into the pure `preflight`. Fail-closed end to end: unreadable → `input_unreadable`; bad YAML → `invalid_spec`; bad project config / unknown config keys → `config_invalid`; wrong invocation → `invalid_invocation`. Exit `0` pass / `2` refuse; `--json` is honoured even when the invocation itself failed (`cli.ts:36-38`) so a stdout-parsing caller always gets a report. Single purpose (the `check` command). `CliIo` is injected, so the command is testable without capturing `process.stdout`.

**`compile.ts` (398, +155)** — owns both directions of the boundary dialect now: `toKernelSpec` (authoring→kernel) and the new `kernelToAuthoring` (kernel→authoring), so `flows check` accepts the compiled canonical JSON as well as authoring YAML. Owning both directions of the one dialect is this module's job. Fail-closes on unknown keys (`assertKernelKeys`) and re-validates a compiled retry policy (`validateKernelRetry`: rejects multiplier 0, jitter >100, max < initial, and any field diverging from the authoring default). `spec-parity.test.ts` pins the round-trip `kernelToAuthoring(toKernelSpec(flow)) === flow`, so the dialect is lossless. Helpers are small and per-concern (`requireKernelObject`, `copyDefined`, `kernelVerificationToAuthoring`, …). Still cohesive as "the boundary dialect translator," but it is the second-largest SDK file — see watch #2.

**`validate.ts` (454, +51)** — a single `Validator` class with per-concern methods (`validateTriggers`, `validateLlm`, `validateAgent`, `validateCli`, `validateSurfaces`, `validatePermissions`, …). Still single-purpose (authoring-spec validation) and cohesive, but **this is the file closest to the 500-line smell** — see watch #1. The version check tightened correctly: the loose `SEMVER_RE` is replaced by an exact match against `SPEC_SCHEMA_VERSION`, mirroring the kernel's `UnsupportedVersion` rejection — symmetric fail-closed on version at both sides of the boundary.

**`spec.ts` (268, +25)** — pure boundary-contract types. Adds `cli` to `LlmStepSpec`/`AgentStepSpec`, `TriggerSpec`, `KernelTriggerSpec`; makes `name?: string`. The `name` optional change is a parity fix aligning SDK with the kernel (`spec.rs` already had `name: Option<String>`). Correct direction.

**`index.ts` (112, +22)** — barrel re-exports of the new preflight/failure-kinds surface. Single purpose.

## 3. Tests — pin deterministic code, with controls against false greens

- `preflight.test.ts` pins resolution order (step→flow→project, never guessing a platform default), the five refusal kinds, the three warning kinds, and that warnings are never silent. A reachability test asserts every declared kind is produced by some path; the converse (no undeclared kind) is held by the typed union + `tsc`.
- `cli.test.ts` uses the canonical ladder flows as refusal subjects and — crucially — includes a *control*: relocated-but-unmutated ladder flows still pass, so the refusals can't be an artifact of the temp directory. That is the "would fail for the wrong reason" guard AGENTS.md rule 5 demands. Asserts exit `2` + typed kind + no `SyntaxError` leak.
- `spec-parity.test.ts` adds the kernel-dialect round-trip.
- `validate.test.ts` adds version-parity (exact match), optional-name, and trigger/CLI fail-closed cases.

## 4. Coupling — symmetric at the seam (AGENTS.md rule 3)

Kernel ↔ SDK coupling is the spec (the journal-protocol boundary). `KernelRunSpec`/`KernelTriggerSpec` mirror the kernel's `RunSpec`/`TriggerSpec` field-for-field, and `spec-parity.test.ts` (SDK) + `spec_parity.rs` (kernel) pin one dialect. Adding `cli`/`triggers` to both sides keeps the seam symmetric. The two sides independently enforce the same invariants (duplicate trigger ids, empty cli, exact version) — that is defense-in-depth at the boundary, not duplication-as-smell: a compiled bundle could reach the kernel without passing the SDK validator. `preflight.ts` is decoupled from I/O via `PreflightProbes` (dependency inversion); `cli.ts` is the only composition root. `failure-kinds.ts` is the shared closed taxonomy, appropriately central. `CliIo` keeps `cli.ts` decoupled from `process.stdout`.

## 5. `workflows/review-swarm.yaml` — the review system as a relayflow

Structurally a relayflow realizing RFC §2 rule 7: three agent lenses (maintainability/history/structure), three model families (claude/codex/opencode) so a shared blind spot in one harness doesn't become the team's. Serialized via `maxConcurrency: 1` because the evidence commits share one git index. The aggregate deterministic step fails the run if **any** lens rejects, and treats a missing/empty/**uncommitted** transcript as a refusal — "an unpersisted verdict is not evidence." That is fail-closed (AGENTS.md rule 4) applied to the review system itself, and it is the right shape.

## Watch items (non-blocking)

1. **`validate.ts` is at 454 lines — within ~10% of the 500-line smell (AGENTS.md rule 1).** Still single-purpose and cohesive, but the next addition (another step kind, another declared field) should trigger a split — e.g. per-step-kind validators into a `validate/` submodule, or extract the key-set tables. This is the file most at risk of growing past its purpose; flag it now.
2. **`compile.ts` is at 398 lines** and now does two related things (authoring→kernel and kernel→authoring). Still cohesive as "the boundary dialect translator," but if `kernelToAuthoring` grows another ~100 lines, split into `compile.ts` + `decompile.ts` (or a `dialect/` pair) so neither half approaches 500.
3. **Duplicated trivial guards** (`isObject`, `isNonEmptyString`) now exist independently in `validate.ts`, `compile.ts`, and `cli.ts`. Each is a 2-line pure helper and the duplication avoids cross-file coupling for a tiny utility — acceptable today. If a fourth consumer appears, extract to a shared `sdk/src/internal/util.ts`.
4. **`isKernelSpec` (`cli.ts:228-235`) is a dialect sniff, not typed dispatch.** It picks the boundary dialect when *any* kernel-only step key (`depends_on`, `max_iterations`, `retry`, `timeout_ms`, `recovery_mode`) is present. It lives in the I/O layer where dialect detection belongs, but a heuristic can misfire on a minimal authoring step that happens to set `max_iterations` (which is legal in authoring too). The comment acknowledges this. Low risk today because the round-trip is pinned; worth a typed discriminator (e.g. an explicit `"dialect": "kernel"` marker or a `flows check --dialect` flag) if `check` ever has to dispatch on ambiguous input.
5. **The kernel now carries `cli`/`triggers` as first-class spec fields.** The "inert" line is held today by the load-bearing comments (`spec.rs:76-82`, mirrored in `spec.ts:152-156`) plus the kernel doing no I/O against them. Defend this boundary against any future PR that moves trigger *matching* or CLI *resolution* into the kernel — that would be the actual violation this PR carefully avoids.

## What this PR does *not* do (and is right not to)

- Does not add a `type: integration` step or any new step verb (RFC settled decisions #1/#13).
- Does not put CLI auth probing or executor lookup in the kernel — all of that is SDK-side behind injected probes.
- Does not grow any file past 500 lines.
- Does not introduce a silent fallback: every refusal and every probe failure carries a declared `completionReason` / kind from the closed taxonomy.

## Conclusion

The shape matches RFC-0001 and AGENTS.md. The kernel stays small and pure (inert declarations, shape validation only, no I/O, no new primitive); product logic lives in SDK helpers behind injected probes; the failure taxonomy is closed and made structural; `completionReason` discipline is pinned by a new kernel test; the boundary dialect is symmetric and round-trip-pinned. No file crosses the 500-line smell — `validate.ts` (454) is the one to watch. No structural blocker.
