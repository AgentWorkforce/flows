## 1. Kernel purity (AGENTS.md rule 2) — PASS

The kernel changes are confined to `kernel/relayflowd-core/src/spec.rs` (+56)
and its tests. `RunSpec` gains two fields:

- `cli: Option<String>` — "Default CLI for llm/agent steps. Preflight resolves
  step → flow → project config before the kernel is asked to start a run."
- `triggers: Vec<TriggerSpec>` — "Inert gate-1 declarations. Matching and
  dispatch belong to gate 2."

`TriggerSpec` is `{ id, executor }` with `#[serde(deny_unknown_fields)]`. The
kernel does **structural validation only**: non-empty id/executor, unique ids,
non-empty cli on steps and flow header. It does **not** resolve CLIs, invoke
providers, match events, dispatch triggers, or perform I/O. A grep of the
kernel diff for `tenant_id`, `reqwest`, `tokio::fs`, `std::fs`, `spawn`,
`http`, `client`, `sdk` returns **NONE FOUND**. This is data carriage + boundary
validation, not product logic. The kernel remains built against a simulated
clock with no I/O in core logic. Decision #15 (tenant-unaware) holds: no
`tenant_id` enters the kernel.

The `cli`/`triggers` fields are carried in the content-addressed spec so
preflight can check executor registration and CLI health before the run starts,
and so the sealed bundle records provenance. That is the correct reason to carry
surface data through the boundary — the kernel hashes it, it does not act on it.

## 2. Closed kernel vocabulary (RFC decision #13, AGENTS.md rule 7) — PASS

Step kinds are unchanged: `Deterministic`, `Llm`, `Agent` (spec.rs:222-224). No
new step verb, no new resident verb. `cli` is an optional field on `Llm`/`Agent`
variants, not a step type. `triggers` is a field on `RunSpec`, not a kernel
mechanism. The three step verbs + four resident verbs are the whole kernel
language; this PR adds nothing to that closed set. Gate 6 holds: no
`integration` primitive is introduced.

## 3. Helpers over primitives (gate 6, decision #13) — PASS

Everything new that *acts* lives in the SDK surface, not the kernel:

- `sdk/src/preflight.ts` — a **pure** evaluator ("Environment facts are
  injected; this module performs no I/O"). CLI resolution, refusal, and warning
  predicates are helpers over the spec, not kernel primitives.
- `sdk/src/cli.ts` — the I/O surface that wires real probes (`spawnSync`
  `<cli> auth status`, `which`, `accessSync`) and filesystem reads. All I/O is
  isolated here.
- `sdk/src/failure-kinds.ts` — a closed refusal/warning taxonomy as `as const`
  arrays + a type guard. Surface vocabulary, not kernel types.

The `<cli> auth status` contract documented in `docs/SURFACE.md` is a surface
convention preflight probes against; the kernel has no notion of it. This is the
helpers-over-primitives shape the RFC demands.

## 4. Fail-closed (AGENTS.md rule 4, RFC covenant 2) — PASS

Fail-closed is enforced at every layer:

- **preflight.ts**: a probe that throws → `probe_failed` **refusal** (not
  silence). Missing binary → `cli_missing`. Non-zero auth → `cli_unauthenticated`.
  No resolution at step/flow/project → `cli_unresolved`. No registered executor
  → `no_executor`. No silent fallback anywhere.
- **validate.ts**: unknown keys are rejected, not dropped — a typo'd `worker` on
  a trigger is surfaced as `unknown key "worker"`. Empty cli/executor refused.
  Version must equal the supported schema version exactly.
- **kernel spec.rs**: `deny_unknown_fields` on `RunSpec`/`TriggerSpec`; empty
  cli, empty/duplicate trigger ids → `SpecError`. `reject_unknown_step_fields`
  enforces the per-type key whitelist on flattened step objects.
- **cli.ts**: unreadable flow → `input_unreadable`; invalid YAML → `invalid_spec`;
  bad project config → `config_invalid`. All map to declared `CheckFailureKind`s
  with exit 2.

The one warn-not-refuse path — a deterministic command whose first word does not
resolve as an executable — is **justified, not silent**: `exec_det.rs` runs
string commands through `/bin/sh -c`, so the word may be a shell builtin,
function, or assignment. Covenant 2 explicitly permits "refuses **or** warns";
this warns with a declared kind (`command_unresolved` / `unprovable_effects` /
`command_unprovable`) and never falls silent. The residual gap (path-like
nonexistent command words are not refused) is **filed in `ops/BACKLOG.md`** as a
deliberate, tracked deferral — not a hidden fail-open.

## 5. completionReason discipline (AGENTS.md rule 4, RFC covenant 2) — PASS

New kernel test `every_failed_run_terminates_with_declared_completion_reasons`
(machine/tests.rs) enumerates the **entire** `CompletionReason` enum —
`VerificationFailed`, `RetriesExhausted`, `LeaseExpired`, `Crashed`, `Timeout`,
`WorkerError`, `BudgetExceeded`, `Canceled` — and for each proves (a) the failed
attempt appends a `StepCompletedPayload` carrying that exact `completion_reason`,
and (b) the run terminates in `RunCompletionReason::StepFailed`. This pins the
closed failure taxonomy end-to-end: no failed run can end in a raw error or an
undeclared reason.

## 6. Tests pin deterministic code (AGENTS.md rule 5) — PASS

- `preflight.test.ts`: pure-predicate tests with injected probes (no I/O). Pins
  resolution order (step→flow→project, no guessed platform default), the four
  refusal kinds, and the three warning kinds.
- `cli.test.ts`: end-to-end through `runCli` with an injected `CliIo`, hermetic
  temp dirs, and fixture executables. Critically, the refusal faults are induced
  on the **actual ladder flows** (the literal subject of the gate clause), with a
  relocated-but-unmutated control case so the suite cannot be green for the wrong
  reason.
- `spec-parity.test.ts`: round-trip `kernelToAuthoring(toKernelSpec(flow)) ===
  flow` for all three ladder flows; empty-triggers normalization; refuses an
  unrepresentable kernel retry policy; canonical JSON/hash pins unchanged.
- `validate.test.ts`: fail-closed on unknown trigger/CLI keys, optional name,
  supported-version-only.
- `kernel spec/tests.rs`: `preflight_data_is_fail_closed` — `deny_unknown_fields`
  rejects an extra `worker` key; empty step cli refused.

## 8. Coupling & boundaries — PASS

The SDK dependency graph is a clean DAG: `failure-kinds.ts` ← `preflight.ts` ←
`cli.ts`; `spec.ts` ← `compile.ts` ← `cli.ts`; `spec.ts` ← `validate.ts`. No

injected probes — the evaluator is testable without a filesystem. This is the
correct separation.

## Watch-level items (non-blocking)

These are not defects against this PR. They are the rungs to watch as the ladder
grows, recorded so the next reviewer has them.

### W1 — compile.ts is accruing a third concern (384 lines, +151 this PR)
`compile.ts` now holds three compilation directions: `compileSpec`
(authoring→normalized), `toKernelSpec` (authoring→kernel), and `kernelToAuthoring`
(kernel→authoring, +~140 lines with helpers). It is single-purpose enough today
(all spec compilation across the boundary) and well under 500. But
`kernelToAuthoring` is the natural extraction candidate — it is the inverse
direction with its own helpers (`requireKernelObject`, `assertKernelKeys`,
`copyDefined`, `kernelStepToAuthoring`, `kernelVerificationToAuthoring`,
`kernelBudgetToAuthoring`, `kernelPermissionsToAuthoring`). If compile.ts takes
one more direction or crosses ~430 lines, split `kernelToAuthoring` into its own
module rather than appending again.

### W2 — validate.ts (454) and spec.rs (451) are approaching the 500-line smell line
Neither needs splitting today. AGENTS.md says a file approaching 500 is a design
smell to "justify it or split it." Both are justified for now: `spec.rs` is the
one dialect definition at the boundary (its header documents that role);
`validate.ts` is one `Validator` class with per-section methods. But both are
within ~50 lines of the line. The next field added to either should trigger a
split, not another append — `validate.ts` in particular could shed
trigger/permissions/budget validation into per-section helpers.

### W3 — `isKernelSpec` dialect detection is a key-sniff heuristic (cli.ts)
`cli.ts` detects whether input is a kernel spec by sniffing for kernel-only keys
(`depends_on`, `max_iterations`, `retry`, `timeout_ms`, `recovery_mode`). It is
pragmatic and correct for the canonical flows (round-trip tests cover them), but
it is a heuristic: a kernel spec whose steps omit all those keys would be
misclassified as authoring. Acceptable for gate 1; worth revisiting as the spec
grows toward a stable discriminator (e.g. an explicit dialect marker).
