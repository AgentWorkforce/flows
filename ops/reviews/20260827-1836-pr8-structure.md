## 1. The kernel boundary — clean

The central structural question is whether `cli` and `triggers` on `RunSpec` put product logic in the kernel. They do not.

- `spec.rs:32-38` — `cli` is annotated *"Preflight resolves step → flow → project config before the kernel is asked to start a run."*; `triggers` is annotated *"Inert gate-1 declarations. Matching and dispatch belong to gate 2."* The kernel **carries** these; it does not interpret or execute them.
- The kernel performs **shape validation only**: empty cli → `EmptyCli`/`EmptyStepCli`; trigger with empty id/executor → `InvalidTrigger`; duplicate id → `DuplicateTrigger`; `TriggerSpec` is `#[serde(deny_unknown_fields)]` so a guessed `worker` field is rejected. This mirrors how the kernel already carries `budget` (journaled, not computed) and `recovery_mode` (policy, not executed).
- No I/O is added to the kernel: it never resolves a binary, never runs `auth status`, never matches a trigger. All of that lives in `sdk/src/preflight.ts` + `sdk/src/cli.ts` — exactly where RFC §4 says TypeScript product-touching code belongs.

**No new primitive.** `cli` is a field on two *existing* step kinds (`Llm`, `Agent`), not a new step verb. `TriggerSpec` is inert data feeding the existing `on` resident verb (RFC settled decision #13: the kernel language is `run`/`llm`/`agent` + `on`/`human`/`dispatch`/done`), not a trigger execution mechanism. Preflight is a *helper*, SDK-side — "helpers over primitives" held.

**completionReason discipline is strengthened, not weakened.** `machine/tests.rs:65` (`every_failed_run_terminates_with_declared_completion_reasons`) pins that every failure kind (VerificationFailed, RetriesExhausted, LeaseExpired, Crashed, Timeout, WorkerError, BudgetExceeded, Canceled) produces a typed `completionReason` on the step completion **and** the run terminates in the journal with a declared enum (`RunCompletionReason::StepFailed`). This is exactly the RFC §1 / AGENTS.md rule 4 gate.

**fail-closed.** `spec/tests.rs:119` (`preflight_data_is_fail_closed`) pins `deny_unknown_fields` on triggers and empty-cli rejection. No silent acceptance.

## 2. The SDK side — single-purpose, I/O at the edges

**`preflight.ts` (221, new)** — pure predicates. The load-bearing line: *"Environment facts are injected; this module performs no I/O."* All environment access is behind the `PreflightProbes` interface, so the predicates are testable against a simulated environment — the SDK-side analogue of the kernel's "built against a simulated clock" rule. Probe exceptions are caught and mapped to a declared kind (`probe_failed`); the test asserts `not.toContain('raw secret')`, so no raw stack trace leaks (AGENTS.md rule 4). A deterministic step is never silently accepted: each leaves exactly one declared warning (`unprovable_effects` / `command_unresolved` / `command_unprovable`) — covenant 2's "refuses *or* warns, never silent." Clean, single-purpose.

**`failure-kinds.ts` (43, new)** — the closed refusal/warning taxonomy as `as const` arrays with derived union types and an `isCheckFailureKind` guard. The closed failure set (RFC covenant 2) made structural. `cli.test.ts` pins that every input-refusal path maps to a declared kind with no raw exceptions, and that the union is exhaustive. Single purpose, tiny.

**`cli.ts` (241, new)** — the `flows check` I/O composition root. This is where I/O *should* live. It injects real `systemProbes` (`spawnSync`/`which`/`accessSync`) into the pure `preflight`. Fail-closed end to end: unreadable → `input_unreadable`; bad YAML → `invalid_spec`; bad project config / unknown config keys → `config_invalid`; wrong invocation → `invalid_invocation`. Exit 0 pass / 2 refuse; no silent success. Honors `--json` even when the invocation itself failed. Single purpose (the `check` command).

**`compile.ts` (389, +155)** — adds `kernelToAuthoring`, the inverse of `toKernelSpec`, so `flows check` accepts the compiled kernel-dialect canonical JSON as well as authoring YAML. Owning both directions of the boundary dialect is this module's job. Fail-closes on unknown keys (`assertKernelKeys`) and validates compiled retry policy (`validateKernelRetry`: rejects multiplier 0, jitter >100, max < initial). `spec-parity.test.ts` pins the round-trip `kernelToAuthoring(toKernelSpec(flow)) === flow`, so the boundary dialect is lossless. Helpers are small and per-concern.

**`validate.ts` (454, +51)** — single `Validator` class, per-concern methods (`validateTriggers`, `validateLlm`, `validateAgent`, `validateCli`, `validateSurfaces`, …). Still single-purpose (spec validation) and cohesive, but **this is the file closest to the 500-line smell** — see watch item #1.

**`spec.ts` (268, +25)** — pure boundary-contract types. Adds `cli`, `TriggerSpec`, `KernelTriggerSpec`; makes `name?: string`. The `name` optional change is a parity fix aligning SDK with the kernel (`spec.rs` already had `name: Option<String>`). Correct direction.

**`index.ts` (112, +22)** — barrel re-exports. Single purpose.

## 3. Tests — pin deterministic code, with controls against false greens

- `preflight.test.ts` pins resolution order (step→flow→project, never guessing a platform default), the five refusal kinds, the three warning kinds, and that warnings are never silent. A reachability test asserts every declared kind is produced by some path; the converse (no undeclared kind) is held by the typed union + `tsc`.
- `cli.test.ts` uses the **canonical ladder flows** as the refusal subjects (RFC §96), and crucially includes a *control* — relocated-but-unmutated ladder flows still pass — so the refusals can't be an artifact of the temp directory. That is exactly the "would fail for the wrong reason" guard AGENTS.md rule 5 demands. Asserts exit 2 + typed kind + no `SyntaxError` leak.
- `spec-parity.test.ts` adds the kernel-dialect round-trip.
- `validate.test.ts` adds version-parity, optional-name, and trigger/CLI fail-closed cases.

## 4. Coupling — symmetric at the seam

Kernel ↔ SDK coupling is the spec (journal protocol boundary). `KernelRunSpec`/`KernelTriggerSpec` mirror the kernel's `RunSpec`/`TriggerSpec` field-for-field, and `spec-parity.test.ts` (SDK) + `spec_parity.rs` (kernel) pin one dialect. Adding `cli`/`triggers` to both sides keeps the seam symmetric. `preflight.ts` is decoupled from I/O via `PreflightProbes` (dependency inversion); `cli.ts` is the only composition root. `failure-kinds.ts` is the shared closed taxonomy, appropriately central.

## 5. `workflows/review-swarm.yaml` — the review system as a relayflow

Structurally a relayflow realizing RFC §2 rule 7: three agent lenses (maintainability/history/structure), three model families (claude/codex/opencode) so a shared blind spot doesn't become the team's. Serialized via `maxConcurrency: 1` because the evidence commits share one git index. The aggregate deterministic step fails the run if **any** lens rejects, and treats a missing/empty/**uncommitted** transcript as a refusal — "an unpersisted verdict is not evidence." That is fail-closed applied to the review system itself. Good shape.

## Watch items (non-blocking)

1. **`validate.ts` is at 454 lines — within ~10% of the 500-line smell.** It is still single-purpose and cohesive, but the next addition (another step kind, another declared field) should trigger a split — e.g. per-step-kind validators into a `validate/` submodule, or extract the key-set tables. This is the file most at risk of growing past its purpose; flag it now.
2. **`compile.ts` is at 389 lines** and now does two related things (authoring→kernel and kernel→authoring). Still cohesive as "the boundary dialect translator," but if `kernelToAuthoring` grows another ~100 lines, split into `compile.ts` + `decompile.ts` (or a `dialect/` pair).
3. **Duplicated trivial guards** (`isObject`, `isNonEmptyString`) now exist independently in `validate.ts`, `compile.ts`, and `cli.ts`. Each is a 2-line pure helper and the duplication avoids cross-file coupling for a tiny utility — acceptable today. If a fourth consumer appears, extract to a shared `sdk/src/internal/util.ts`.
4. **The kernel now carries `cli`/`triggers` as first-class spec fields.** The "inert" line is held today by the load-bearing comments (`spec.rs:32-38`, mirrored in `spec.ts`) plus the kernel doing no I/O against them. Defend this boundary against any future PR that moves trigger *matching* or CLI *resolution* into the kernel — that would be the actual violation this PR carefully avoids.

## What this PR does *not* do (and is right not to)

- Does not add a `type: integration` step or any new step verb (RFC settled decision #1/#13).
- Does not put CLI auth probing or executor lookup in the kernel.
- Does not grow any file past 500 lines.
- Does not introduce a silent fallback: every refusal and every probe failure carries a declared `completionReason`/kind.

## Conclusion

The shape matches RFC-0001 and AGENTS.md. The kernel stays small and pure (inert declarations, no I/O, no new primitive); product logic lives in SDK helpers behind injected probes; the failure taxonomy is closed and made structural; `completionReason` discipline is pinned by a new kernel test; the boundary dialect is symmetric and round-trip-pinned. No file crosses the 500-line smell; `validate.ts` is the one to watch. No structural blocker.

REVIEW_PASSED
