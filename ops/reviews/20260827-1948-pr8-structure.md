## Findings

### 1. The kernel stays pure — inert declarations, no product logic (PASS)

`spec.rs` adds two fields to `RunSpec` and one each to the `Llm`/`Agent` step kinds:

- `cli: Option<String>` — *"Default CLI declaration for llm/agent steps. `flows check`
  resolves step → flow → project config. The kernel treats this as inert data;
  `run.start` does not invoke the surface preflight in gate 1."*
- `triggers: Vec<TriggerSpec>` — *"Inert gate-1 declarations. Matching and dispatch
  belong to gate 2."*
- `TriggerSpec { id, executor }` with `#[serde(deny_unknown_fields)]`.

The kernel does only three things with them: store (serde), structurally validate
(non-empty, unique trigger ids, no unknown keys), and carry them so the canonical spec
can be journaled and hashed. It does **not** resolve CLIs, call CLIs, probe auth, match
events, dispatch, provision workers, or hold any provider SDK. Verified by search:
**no reference to `cli`/`triggers`/`TriggerSpec` anywhere in the kernel outside
`spec.rs`**. The `executor` hits in `machine.rs:218`, `entry.rs:127`, `engine.rs:213`,
`server/session.rs:317`, and `worker.rs:41` are a **different, pre-existing** field —
the *step* executor (`AttemptStartedPayload.executor`, set to `"kernel"` or
`"unassigned"`) — untouched by this PR. The `cli` hits in `main.rs` are the Rust
binary's own `clap` `Cli` struct, not the spec field. No conflation, no leakage.

This is the same "carried and journaled from submit, acted on later" pattern the RFC
already uses for the `budget` envelope (§1, gate 1). Carrying a gate-2 declaration in
the kernel spec is consistent with the spec being the content-addressed composable unit
(settled decision #14: `flows build` seals canonical spec JSON). The kernel hashing it
is correct; the kernel not dispatching it is correct. The inline comments name the
boundary explicitly, which is the discipline AGENTS.md rule 7 asks for.

### 2. No primitive was added — helpers/declarations only (PASS)

RFC settled decision #13: *"Three step verbs (`run`/`llm`/`agent`) + four resident
verbs (`on`/`human`/`dispatch`/`done`) are the whole kernel language. Everything else
… is surface that compiles to kernel primitives."*

This PR adds **zero** verbs. `StepKind` remains `Deterministic | Llm | Agent`.
`TriggerSpec` is a data struct, not a step type. `cli` is a string field on existing
step kinds. There is no `type: integration`, no new resident verb, no kernel-level
"trigger" step. The closed kernel vocabulary is exactly preserved. On the SDK side,
`preflight` is a **surface helper** (a function over injected probes), not a kernel
mechanism; `failure-kinds.ts` is a **surface taxonomy**, not a kernel enum;
`kernelToAuthoring` is a **compiler inverse** (boundary translation), not a primitive.
This is precisely the helper-over-primitive discipline the RFC demands.

### 3. Fail-closed is enforced at every layer (PASS)

- **Kernel `spec.rs`:** new `EmptyCli`, `InvalidTrigger`, `DuplicateTrigger`,
  `EmptyStepCli` `SpecError` variants; `deny_unknown_fields` on `TriggerSpec` rejects
  an extra `worker` key at parse (pinned by `spec/tests.rs::preflight_data_is_fail_closed`).
  `STEP_LLM_FIELDS`/`STEP_AGENT_FIELDS` widened in lockstep for `cli` so the
  unknown-field rejector stays exhaustive.
- **SDK `validate.ts`:** unknown-key rejection (`ROOT_KEYS`, `TRIGGER_KEYS`, per-type
  step keys); version check **tightened** from a permissive semver regex to exact match
  against `SPEC_SCHEMA_VERSION` (stricter, fail-closed on unknown versions); empty
  `cli`, invalid trigger id/executor, and duplicate trigger id are all errors.
- **SDK `preflight.ts`:** `cli_missing` / `cli_unauthenticated` / `cli_unresolved` /
  `no_executor` are refusals; a probe that **throws** becomes `probe_failed` (a
  refusal) — never silently swallowed. A deterministic step always leaves exactly one
  warning (`unprovable_effects` / `command_unresolved` / `command_unprovable`); silence
  is explicitly not an allowed state (`failure-kinds.ts:23-28`). The platform-default
  CLI rung is declared in `SURFACE.md` but **unprovisioned at gate 1**, and a flow that
  reaches it refuses with `cli_unresolved` "rather than guessing" — fail-closed by
  design, not by accident.
- **SDK `cli.ts`:** unreadable input, invalid YAML, invalid spec, invalid config all
  become typed refusals (`input_unreadable`, `invalid_spec`, `config_invalid`); exit 2
  on refusal, 0 on pass. The catch-all at `cli.ts:83-87` maps an unexpected throw to
  `invalid_spec` rather than leaking a stack trace (covenant 2: a raw stack trace is a
  kernel bug; the surface mirrors the discipline).
- **`SURFACE.md` preflightable-CLI contract:** *"preflight never sends a prompt, never
  spends a token, and never invokes any other subcommand"*; a CLI without `auth status`
  is refused as unauthenticated rather than assumed healthy.

### 4. `completionReason` discipline is pinned by a gate test (PASS)

New kernel test `machine/tests.rs::every_failed_run_terminates_with_declared_completion_reasons`
(line 66) iterates the closed set of failure `CompletionReason`s — `VerificationFailed`,
`RetriesExhausted`, `LeaseExpired`, `Crashed`, `Timeout`, `WorkerError`, `BudgetExceeded`,
`Canceled` — and for each asserts: (a) the `StepCompletedPayload.completion_reason`
equals the declared reason, and (b) folding the journal terminates the run with
`RunCompletionReason::StepFailed`. This is RFC covenant 2 (*"every failure is one of a
closed set … journaled with its `completionReason`"*) and AGENTS.md rule 4 (*"Every
completion carries a `completionReason`"*) turned into a crash-gate, not a doc claim.
The test references only real, existing types — it is not dead code. The SDK mirrors
the closed-set discipline with `failure-kinds.ts`'s `as const` tuples and derived types,
and `preflight.test.ts` reaches every declared refusal and warning kind.

One robustness note (non-blocking): the eight variants are enumerated by hand. A ninth
`CompletionReason` added later will not fail this test; the exhaustiveness is by
inspection, not enforced by the compiler. Acceptable today; if the failure set grows,
prefer an exhaustive match the compiler can check.

### 5. Boundaries, coupling, single purpose (PASS)

- **`preflight.ts` (237 lines)** is pure over injected probes — the file states
  *"Environment facts are injected; this module performs no I/O."* It depends only on
  `spec.ts`/`failure-kinds.ts` *types*. Dependency direction is clean: the pure core
  imports nothing from the I/O layer. This mirrors the kernel's "built against a
  simulated clock, no I/O in core logic" discipline (AGENTS.md rule 2) on the SDK side.
- **`cli.ts` (282 lines, new)** is the I/O layer (`fs`, `spawnSync`, `yaml`) that
  wires real probes into `preflight`. It is the `flows` `bin` (`package.json`). I/O
  confined to the surface, pure core kept pure — correct boundary.
- **`failure-kinds.ts` (43 lines, new)** has one purpose: the closed refusal/warning
  taxonomy with type-level derivation.
- **`compile.ts` (408 lines)** gains `kernelToAuthoring`, the inverse of `toKernelSpec`
  (the bijection F5 asked for). It is fail-closed (`requireKernelObject`,
  `assertKernelKeys` reject unknown keys; `validateKernelRetry` rejects non-default
  policy). The reverse map shares the forward map's key lists and helpers; splitting it
  would duplicate. Cohesive, under the 500-line smell threshold.
- **`validate.ts` (454 lines)** is the largest file and the largest risk surface (see
  watch-item W1), but still under 500 and single-purpose (authoring-shape validation).
- **kernel `spec.rs` (452 lines)** — under 500, single purpose (spec parse + validate).
- No file crosses the AGENTS.md 500-line design-smell line; no file mixes purposes.

## Watch-items (non-blocking, for the next lens / epoch)

**W1 — `validate.ts` (454) and `spec.rs` (452) are approaching the 500-line smell
threshold.** AGENTS.md rule 1: *"Any file approaching 500 lines is a design smell;
justify it or split it."* Both are single-purpose today, but the `Validator` class is
accreting nested-structure validators (triggers, cli, surfaces, permissions, budget,
verification), and `spec.rs` owns the spec schema plus all shape validation and gained
`TriggerSpec` + four new `SpecError` variants this PR. Recommendation: before either
crosses 500, extract per-shape validators. `spec.rs` in particular should shed
`TriggerSpec` + trigger validation into a `spec/triggers.rs` submodule **when gate 2
adds real trigger matching** — the kernel will then own the struct it actually acts on,
and the schema file stays small.

**W2 — trigger-shape validation is duplicated across the boundary.**
`SpecError::InvalidTrigger` / `DuplicateTrigger` (kernel `spec.rs`) and
`validateTriggers` (SDK `validate.ts`) check the same shape. Defense-in-depth at the
boundary is reasonable, and the kernel owns the spec schema so validating declared
fields is in-scope — but since the kernel never dispatches triggers (gate 2 does), the
kernel's trigger-shape validation leans toward surface concern leaking into the kernel.
Acceptable today; revisit when gate 2 lands and the kernel has a reason to know trigger
shape beyond "it is journaled."

**W3 — `cli` on `llm` steps.** RFC §1 calls `llm` *"a bare model call — prompt in,
verified output out; no PTY, no sandbox."* Adding `cli` is evidence-driven (the
2026-08-27 dogfood: gemini auth dead, unknown `cli: grok` killed a run at minute 27)
and the kernel never invokes it, so the field is inert and `llm`'s "bareness" — a
kernel-execution property — is preserved. Worth tracking that the bareness invariant is
about *execution*, not *declaration*; it holds today. If a future gate gives the kernel
a reason to read `cli`, the invariant needs a fresh look.

**W4 — version check is exact-match, not a window.** `validate.ts` rejects any version
≠ `SPEC_SCHEMA_VERSION`. RFC §7 leaves the spec-schema version window open. Correct
fail-closed behavior for gate 1 (no N−1 window yet); when a second supported version
lands, this must relax to the window rather than silently refusing valid specs.

**W5 — `isKernelSpec` heuristic** (`cli.ts:244-265`) detects the kernel dialect by
snake-case sentinels plus nested budget/verification/permission shapes. The earlier
rounds' N3 observed a kernel-valid spec omitting every marker routes through the
authoring compiler and fails closed with `invalid_spec`. The widening to budget /
verification / permission shapes closes most of the gap, and every misroute I could
construct fails closed. Robustness note only; a `$schema`/version discriminator would
be the durable shape but is out of scope for this PR (it changes the compiled-spec
format under hash pins on both sides of the boundary).

## Conclusion

The shape matches RFC-0001 and AGENTS.md. The kernel stays small and pure — `cli` and
`triggers` are inert declarations, validated for shape, never acted on; no provider
SDKs, no I/O, no product logic, no tenant awareness leaked in. No primitive was added
where a helper belonged; `preflight` is a surface helper and the kernel vocabulary
stays closed (`deterministic` / `llm` / `agent`). Fail-closed and `completionReason`
discipline are strong and now pinned by a kernel test that iterates the closed failure
set. File sizes are within bounds; `validate.ts` (454) and `spec.rs` (452) are flagged
to split before they cross 500. The judging gate is unchanged from `main` at this head,
so the "never edit a gate that judges your own work" rail holds. No file has grown past
its purpose.

REVIEW_PASSED
