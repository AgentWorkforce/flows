## Assessment against AGENTS.md standards

### 1. Small, single-purpose modules

`cloud-artifact.mjs` is 249 lines — comfortably under the 500-line smell threshold. It is a cohesive tool with one purpose: build and verify the Linux x64 runtime artifact (relayflowd + flows CLI + manifest + checksum). Internally it is partitioned into clearly seamed functions: `buildCloudArtifact`, `verifyCloudArtifact`, `verifyArtifactDirectory`, `createManifest`, `parseManifest`, and small pure helpers (`listFiles`, `sha256File`, `assertRegularFile`, `assertLinuxX64Elf`, `run`, `assertSourceCommit`). No single function is doing two jobs.

The one mild boundary tension: build and verify live in one file. This is defensible — `verify` is the fail-closed counterpart that the build immediately exercises, and the test file imports both. Not a smell.

### 2. Kernel is small and pure — no product logic in the kernel

**No kernel changes at all.** No `relayflowd`, `relayflowd-core`, or `relayflowd-journal` touched. This PR cannot put product logic in the kernel because it does not enter the kernel. ✓

### 3. Journal protocol boundary

Not applicable — no journal/protocol surface is changed. The `manifest.json` it emits (`schemaVersion: 1`, `protocolVersion: "0"`) is a **release-artifact manifest**, not the kernel journal/stream protocol. It is scoped and versioned separately, so it does not dilute the RFC §7 versioning question about journal/spec/SDK protocol. Worth flagging that `protocolVersion` is an overloaded name next to the real journal protocol; a reader glancing at it could confuse the two. Consider renaming (e.g. `artifactVersion`) in a follow-up, but this is naming hygiene, not a structural defect.

### 4. Fail closed

Clean. `verifyCloudArtifact` rejects a non-64-hex checksum and throws on mismatch *before* extraction; `verifyArtifactDirectory` insists on an exact manifest/content match and rejects symlinks, non-regular entries, missing executables, and non-ELF64/Linux/x86-64 binaries. There is no fallback, no `console.warn`, no silent path. `run()` throws on non-zero exit. This matches the RFC covenant-2 discipline (provable at build/verify time) and AGENTS.md "fail closed."

### 5. Tests pin the deterministic code

`cloud-artifact.test.mjs` pins the deterministic contract: (a) build→verify round-trip produces the exact declared file set, (b) tampering a manifested runtime file fails verification (`/file sha256 mismatch/`), (c) outer checksum mismatch fails before extraction. All three are the fail-closed properties. Good coverage for a tooling script.

### 6. No dead code / speculative abstraction

None observed. Every exported function is used by either the CLI `main` or the tests. The manifest schema is versioned but v1-only with a strict parser — no speculative future branches.

### 7. RFC vocabulary — helpers over primitives, closed kernel vocabulary

No kernel vocabulary is added or widened. No new step verbs, no `integration` primitive, no kernel surface. This PR contributes build tooling only. It does not contradict the "typed failure"/`completionReason` discipline because it emits no journal entries.

## Coupling

- The script is **parameterized**: it receives `relayflowd` and `flows-runtime` as inputs rather than reaching into `kernel/target/release` or `sdk/` directly. The CI workflow owns the concrete paths. This keeps `scripts/cloud-artifact.mjs` decoupled from the Rust build output and the SDK CLI build. ✓
- The workflow does duplicate a little verification outside the script (inline `tar -xzf` smoke test, `find`/`awk` checksum extraction). This is acceptable CI plumbing and does not pull product logic anywhere. The script remains the single source of truth for the *contract*.
- `assertLinuxX64Elf` hard-codes 20-byte ELF header inspection in the script rather than shelling out to `file(1)`. Given the sim-tooling context and the goal of zero ambient dependencies, this is a reasonable, deterministic helper.

## Notable observations (non-blocking)

1. **`protocolVersion: "0"` naming** vs. the RFC's journal/SDK protocol — overloaded term; rename to something artifact-scoped to avoid confusion.
2. **RFC decision #14 vs. this PR's purpose.** The RFC describes a *flow bundle* addressed as `flow@sha256:…` (compiled spec + dependencies). This PR packages a *runtime* (relayflowd binary + flows CLI), not a flow bundle. The two are distinct and do not conflict, but a future reader should not mistake this "artifact" for decision #14's content-addressed flow bundle. Worth a one-line note in the workflow or README.
3. **Platform fixed to linux/x64.** The script asserts ELF64/linux/x64 and the manifest hard-codes `platform: "linux"`, `arch: "x64"`. Adding macOS/ARM would require generalization. Not a defect for a cloud-runtime artifact; just noting the current scope is deliberately single-platform.

## Verdict

The PR is structurally sound. It is small, well-seamed, fail-closed, test-pinned, and entirely absent from the kernel, so it cannot violate the closed-kernel-vocabulary or completionReason constraints. The two observations above (protocol naming, artifact-vs-bundle distinction) are naming/documentation hygiene, not blockers.

REVIEW_PASSED
