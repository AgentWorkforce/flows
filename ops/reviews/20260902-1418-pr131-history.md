# History Review — PR #131

**Lens:** does the change fit the story of the code?

**Reviewed commit:** `46ce1623e99f43d06a692cb49d657ef602c1b096`
(`feat(release): build verified Cloud v2 runtime artifact`), one commit ahead of
`origin/main` at `51415d9`.

## Verdict

No blocking historical inconsistency found. This is a release-tooling addition
around the already-settled Rust-kernel / TypeScript-surface split; it neither
changes the journal protocol nor invents a new kernel primitive. The commit
subject tells the truth about its diff: the commit adds a Linux x64 runtime
archive builder, a strict verifier, regression tests, and a GitHub job that has
actually built, verified, smoke-tested, and uploaded that archive.

## Findings

No blocking findings.

### 1. The runtime archive does not contradict RFC-0001 decision 14

RFC-0001 decision 14 and `docs/SURFACE.md` define a **flow bundle**:
canonical spec, compiled dialect, pinned dependencies, helpers/assets,
preflight declaration, and identity signature, addressed as
`flow@sha256:...`. PR #131 instead packages the **runtime that executes those
bundles**: `relayflowd`, the `flows` CLI, and a runtime manifest. Keeping these
as separate artifact classes fits the RFC's other settled boundary: the
kernel/control plane is Rust, user-facing surfaces are TypeScript, and the
journal protocol separates them.

The new archive must not be described later as implementing `flows build` or
the content-addressed production-flow contract—it does not. PR #131 itself
uses the narrower and accurate phrase “Cloud v2 runtime artifact,” so there is
no present contradiction.

### 2. It does not resurrect the build-output failure that history removed

Commit `5132079` deliberately moved Cargo output out of relayflow-propagated
worktrees after `kernel/target/debug` caused 413 flushes and silent work loss.
PR #131 does write its release binary to `kernel/target/release`, but it does so
inside one GitHub Actions job, where steps share the runner filesystem and no
relayfile snapshot propagates the tree. Only `dist/cloud-artifact/*.tar.gz` and
its checksum are uploaded. The old failure's causal boundary is therefore not
reintroduced.

Likewise, the PR does not reverse the earlier de-vendoring decision: it adds no
vendor tree and uses `cargo build --locked`.

to creating `sdk/src/worker.ts`. History shows that package landed in #53:

### 4. Provenance nuance: pull-request artifacts identify the tested merge tree

On the `pull_request` event, the default checkout is GitHub's synthetic merge
ref. Consequently `git rev-parse HEAD`, the manifest's `sourceCommit`, the
archive filename, and `${{ github.sha }}` all identify merge commit
`41a7783...`, not PR head `46ce162...`. The live job confirms that this is
internally consistent:


That is the exact tree tested, so it is not false provenance. It is, however,

commit should be made explicit. The current `workflow_dispatch` path can build
an actual selected branch commit, and this PR does not claim to publish a
durable release.

## Conclusion

PR #131 is a coherent next layer above the kernel and SDK already present in
history. It avoids the repository's recorded failure classes, preserves the
RFC's kernel/surface boundary, and does not masquerade as the still-unbuilt
content-addressed flow-bundle feature. The only cautions are future-facing:
keep runtime archives distinct from flow bundles, and choose/document the
source ref explicitly before treating a PR-validation artifact as a durable
release.

REVIEW_PASSED
