## Findings against the structure rubric

### 1. Product logic in the kernel? No.
The new `cli` and `triggers` fields are **inert data**, not logic. Proof:

```
$ rg -n 'cli|triggers|TriggerSpec' kernel/relayflowd-core/src/machine.rs \
    kernel/relayflowd-core/src/entry.rs kernel/relayflowd-core/src/journal.rs \
    kernel/relayflowd-core/src/state.rs kernel/relayflowd-core/src/verify.rs
NONE — inert fields do not touch kernel runtime
```

The kernel runtime (`machine`, `entry`, `journal`, `state`, `verify`) never references them.
`spec.rs` only *parses, shape-validates, and serializes* them — exactly what a content-addressed
boundary spec must do (settled decision #14: runs reference digests; the kernel and SDK must
stamp the same hash, which the `spec_parity` tests prove). The field comments state the contract
explicitly: *"The kernel treats this as inert data; `run.start` does not invoke the surface
preflight"* and *"Matching and dispatch belong to gate 2."* No provider SDK, no I/O, no tenant
awareness entered the kernel. §4 of the RFC holds.

### 2. Primitive added instead of a helper? No.
The kernel step-verb vocabulary stays closed at `deterministic` / `llm` / `agent` (RFC §1,
settled decision #13). **No new step verb and no resident verb (`on`/`human`/`dispatch`/`done`)
was added.** `TriggerSpec` is a plain `#[serde(deny_unknown_fields)]` data struct, not a
primitive; triggers are declarations the *surface* preflight checks and gate 2 will dispatch.
On the SDK side the preflight logic is a **pure helper** — `preflight.ts` does no I/O; all
environment facts enter through the injected `PreflightProbes` interface (`cli`, `executor`,
`command`). The I/O shell (`cli.ts`'s `systemProbes`) is the only place that touches `fs`/`spawn`.
This is the correct helper-over-primitive, purity-at-the-core split.

### 3. Fail-closed & completionReason discipline? Enforced and tested.
- Kernel `TriggerSpec` carries `deny_unknown_fields`; `validate()` rejects empty flow `cli`,
  empty/duplicate trigger `id`/`executor`, and empty per-step `cli` (new `SpecError` variants
  `EmptyCli` / `InvalidTrigger` / `DuplicateTrigger` / `EmptyStepCli`).
- Preflight refuses (`severity: 'refusal'`) on a **closed** set: `cli_missing`,
  `cli_unauthenticated`, `cli_unresolved`, `no_executor`, `probe_failed`. A deterministic step
  is never silently accepted — it always leaves exactly one warning (`unprovable_effects` /
  `command_unresolved` / `command_unprovable`), satisfying covenant 2's "refuses *or warns* on
  anything it cannot prove." The taxonomy lives in one 43-line module (`failure-kinds.ts`).
- `completionReason` discipline is pinned by a new test that iterates the closed failure enum
  and asserts each failed attempt appends a typed `StepCompletedPayload` and the run terminates
  in a declared `RunCompletionReason::StepFailed` — never a raw error.

### 4. File size & single purpose? All under 500; two placement notes.
Largest files touched or relevant: `sdk/src/validate.ts` 454, `kernel/relayflowd-core/src/spec.rs`
452, `sdk/src/compile.ts` 408, `sdk/src/cli.ts` 311. None cross the 500-line smell line; none
approach the old 11,560-line runner anti-pattern. Two placement refinements worth naming:

- **(minor) `kernelDialectMarker` lives in the I/O shell.** `cli.ts` carries a heuristic that
  detects whether input is authoring or kernel dialect and, if kernel, calls `kernelToAuthoring`.
  Dialect detection is a *spec-boundary translation* concern and would sit more naturally in
  `compile.ts` (which already owns both translation directions) than in the I/O entrypoint. Today
  it is harmless — `cli.ts` is 311 lines and cohesive as the I/O shell — but it is the one piece
  of non-I/O logic in that file.
- **(minor) `compile.ts` is now bidirectional and is the largest growth.** It gained
  `kernelToAuthoring` plus eight helpers (`kernelStepToAuthoring`, `validateKernelRetry`,
  `kernelVerificationToAuthoring`, `kernelBudgetToAuthoring`, `kernelPermissionsToAuthoring`,
  `requireKernelObject`, `assertKernelKeys`, `copyDefined`). At 408 lines it is still
  single-purpose ("spec boundary translation, both directions") and under the line, but the
  inverse direction is the natural split candidate if either direction grows further, so each
  stays plainly single-purpose.

Neither is "a file grown past its purpose" today; both are forward-looking notes.

### 5. Boundary parity? Held.
`name` became optional in the SDK `FlowSpec` (was required); the kernel `RunSpec.name` was
already `Option<String>`, so this *removes* a pre-existing SDK/kernel divergence rather than
introducing one. `cli`/`triggers` round-trip through `toKernelSpec` / `kernelToAuthoring` and the
kernel omits an empty trigger list on serialize, which `compileSpec` normalizes — one hashable
form on both sides. The `spec_parity` tests (3) pass with the new fields present.

tests. All files are under the 500-line smell line. Two minor placement notes (dialect detection
in the I/O shell; `compile.ts` now bidirectional and the largest growth) are refinements for a
future rung, not gate-blockers.
