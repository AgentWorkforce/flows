### `compileSpec` and `toKernelSpec`

There are two intentionally supported lowering paths:

1. `compileSpec` runs `validateSpec`, then `compileStep` replaces valid `output` sugar with authoring-form `{type: 'json_schema', schema}`. The normalized step contains no `output` property.
2. A typed caller may pass a raw `FlowSpec` directly to exported `toKernelSpec`. `toKernelVerification` handles raw `output` for both `llm` and `agent`, delegates malformed/conflict checks to the same validator, and returns the existing `{json_schema: ...}` kernel form.

No new field crosses the journal protocol boundary. The canonical hn-monitor kernel fixture is unchanged even though the authoring YAML now uses `output:`.

### Fail-closed behavior and v1 compatibility

The step-key allowlists admit `output` only for `llm` and `agent`. Deterministic use and a misspelled `outputs` key are refused. Any simultaneous `output + verification` declaration is refused, including legacy `exit_code`, `output_contains`, and `json_schema` forms. Non-object declarations are refused. JSON Schema objects themselves remain open to JSON Schema vocabulary rather than being incorrectly checked against Relayflow keys.

The legacy explicit `verification: {type: 'json_schema', schema}` path remains valid and lowers identically. This preserves the current v1 authoring form; the new syntax is additive sugar.
