## Verdict on each structural axis

### 1. Kernel purity — PASS (with one named tension)

AGENTS.md #2: the kernel holds journal, scheduler, leases, durable timers,
streams — no provider SDKs, no product logic, no tenant awareness, no I/O in
core logic.

The kernel additions are exactly three inert spec fields:
- `RunSpec.cli: Option<String>` (`spec.rs:35-36`)
- `RunSpec.triggers: Vec<TriggerSpec>` (`spec.rs:38-39`)
- `cli: Option<String>` on `StepKind::Llm` and `StepKind::Agent` (`spec.rs:243,248`)
- `TriggerSpec { id, executor }` (`spec.rs:336-341`)

I grepped every `*.rs` under `kernel/` for `.cli`, `.triggers`, and
`TriggerSpec`. Result: **only `spec.rs` (definition + `validate`) and
`spec/tests.rs` (assertions)**. No reference in `machine.rs`, `engine.rs`,
`server.rs`, `server/session.rs`, the journal crate, or the crash-resume
tests. The kernel parses these fields, structurally validates them, journals
them as part of `RunSpec`, and never acts on them. The comments say "inert"
(`spec.rs:32-34, 37-38`) and the code matches the comment.

No provider SDK, no CLI invocation, no trigger matching/dispatch, no tenant
awareness, no I/O entered the kernel. The preflight that *does* invoke CLIs
lives entirely in the SDK surface (`sdk/src/preflight.ts`, `sdk/src/cli.ts`).
Correct boundary.

**N1 (non-blocking observation — the PR's most arguable structural decision):**
`triggers` / `TriggerSpec` is gate-2 vocabulary ("a relayflow can power a
proactive agent," RFC §3 gate 2) carried as inert, unconsumed data into the
gate-1 kernel. AGENTS.md #6 says "no speculative abstraction; build what the
current gate needs." The kernel validates trigger structure (`InvalidTrigger`,
`DuplicateTrigger`, `spec.rs:73-81`) for a gate whose dispatch does not exist
yet, and no kernel behavior reads the field. This is defensible — the kernel's
`deny_unknown_fields` contract (`spec.rs:24`) means it *must* declare every
field the spec can carry or it will refuse valid specs, and structural
validation is consistent with how it validates steps (non-empty id, no dup) and
fail-closed (covenant 2). But it is the edge of "speculative": gate-2 shape in
the gate-1 kernel ahead of any gate-1 consumer. The `cli` field is in the same
inert category but more justified — an `llm`/`agent` step declaring its
executor is part of the step's identity, and gate-1's own `flows check`
preflight reads it. Noting, not blocking.

### 2. Closed kernel vocabulary — PASS

RFC settled decision #13: three step verbs (`run`/`llm`/`agent`) + four
resident verbs; everything else is surface. AGENTS.md #7: step types are
`deterministic`, `llm`, `agent`.

No new step type was added. `StepKind` is still `Deterministic | Llm | Agent`
(`spec.rs:232`). `TriggerSpec` is a **data struct, not a kernel verb** — no
scheduling, no matching, no dispatch. The preflight refusal taxonomy is a
*closed* set declared in the SDK surface (`sdk/src/failure-kinds.ts:2-8`):
`cli_missing | cli_unauthenticated | cli_unresolved | no_executor |
probe_failed`, plus input refusals `config_invalid | input_unreadable |
invalid_invocation | invalid_spec`. No new kernel primitive. Helpers (the
preflight evaluator) live in the surface, compiled from data, not added to the
kernel. This is exactly "helpers over primitives."

### 3. Fail-closed — PASS (strong)

AGENTS.md #4: a journal/spec write that fails fails the step; no silent
fallbacks; every completion carries a `completionReason`.

- `TriggerSpec` carries `#[serde(deny_unknown_fields)]` (`spec.rs:337`) — an
  unknown trigger key is `Malformed`, not dropped. Verified by
  `preflight_data_is_fail_closed` (`spec/tests.rs:227-235`).
- `EmptyCli`, `InvalidTrigger`, `DuplicateTrigger`, `EmptyStepCli` all *refuse*
  (`spec.rs:69-81, 94-100`), pinned by the same test (`spec/tests.rs:237-276`).
- SDK `validate.ts` refuses unknown keys at every object level with a
  nearest-key suggestion (`validate.ts:76-86, 408-421`).
- The deterministic-command case *warns* rather than refuses, but this is a
  **deliberate, disclosed** limitation: a bare command word may be a shell
  builtin/function/assignment under `/bin/sh -c` (kernel `exec_det.rs`), so
  refusing would reject valid flows. It is documented in `docs/SURFACE.md`
  ("Accepted deterministic-command limitation") and tracked in
  `ops/BACKLOG.md` ("Close the deterministic-command preflight gap"). This is
  honest fail-closed — warn where unprovable, refuse where provable — not a
  silent fail-open. The three warning kinds (`unprovable_effects`,
  `command_unresolved`, `command_unprovable`) are themselves a closed set
  (`failure-kinds.ts:29-33`) and every deterministic step emits exactly one
  (`preflight.ts:237-278`), so silence is never a state.

### 4. completionReason discipline — PASS (reinforced)

RFC covenant 2 / AGENTS.md #4: every failure is a closed declared kind;
every completion carries a `completionReason`.

The new kernel test `every_failed_run_terminates_with_declared_completion_reasons`
(`machine/tests.rs:66-104`) enumerates **all eight** `CompletionReason`
failure variants (`VerificationFailed, RetriesExhausted, LeaseExpired, Crashed,
Timeout, WorkerError, BudgetExceeded, Canceled`) and proves each (a) serializes
to the closed `StepCompletedPayload`, (b) carries the matching
`completion_reason`, and (c) terminates the run as a typed
`RunCompletedPayload` with `RunCompletionReason::StepFailed`. This is exactly
the "closed taxonomy pinned by a test" the RFC demands. No raw error path was
added.

**N2 (non-blocking — single-purpose watch):** `sdk/src/cli.ts` (311 lines)

### 6. Journal protocol is the boundary — PASS

AGENTS.md #3: SDKs and surfaces speak the journal protocol; nothing reaches
around it.

The kernel changes are confined to the spec parser/validator and one machine
test. No journal entry type was added, no scheduler/engine/server behavior
changed. The preflight (`sdk/src/preflight.ts`) is a **pure** module — its
probes are injected (`PreflightProbes`, `preflight.ts:41-46`), it performs no
I/O of its own, and it never touches the journal. The I/O-bound probe
implementation lives in `cli.ts` (`systemProbes`, `probeCli`) and is the
entrypoint's job, not the pure evaluator's. Clean separation.

### 7. Coupling — PASS (intended, pinned)

The SDK and kernel spec shapes are coupled by design — one boundary dialect
(RFC §4, settled decision #5). `cli` and `triggers` exist in both
`sdk/src/spec.ts` (authoring `FlowSpec` + kernel `KernelRunSpec`) and
`kernel/relayflowd-core/src/spec.rs`, and the round-trip is pinned by
`sdk/tests/spec-parity.test.ts` and the kernel's `spec_parity.rs` over shared
`testdata/`. `compile.ts` carries both fields through `toKernelSpec`
(`compile.ts:151-152`) and the inverse `kernelToAuthoring`
(`compile.ts:180, 224, 231`). The coupling is explicit, symmetric, and tested —
not hidden reach-around.

**N4 (process, not code):** the diff carries ~50 review-transcript files under
`ops/reviews/` and ~1,400 lines appended to `ops/DRIVE-LOG.md`. These are
append-only process logs, not source modules, so the 500-line / single-purpose
rule does not apply. But the process-artifact volume (~16,000 of 17,299 diff
lines) dwarfs the ~1,077 lines of actual source. This is a signal-to-noise
observation for the diff, not a code-structure defect.

## Summary

Through the single lens of structure, no blocking defect was found:

- No product logic entered the kernel (no SDK, no I/O, no dispatch, no tenant
  awareness); `cli`/`triggers` are inert spec data the kernel carries for
  parity and validates structurally.
- No new kernel primitive was added (`TriggerSpec` is data, not a verb); the
  preflight evaluator is a surface helper, not a kernel addition.
- Fail-closed holds at every seam (`deny_unknown_fields`, empty/duplicate
  refusals, closed warning + refusal taxonomies, documented warn-not-refuse
  limitation).
- The `completionReason` closed taxonomy is reinforced by an exhaustive
  8-variant kernel test.
- No source file reaches 500 lines; the two closest (`validate.ts` 454,
  `spec.rs` 452) remain single-purpose.
- The journal protocol boundary is respected; the pure preflight evaluator is
  cleanly separated from its I/O-bound probes.

Non-blocking observations carried forward:
- **N1:** `triggers`/`TriggerSpec` is gate-2 vocabulary carried as inert,
  unconsumed data into the gate-1 kernel — defensible under the
  `deny_unknown_fields` contract but at the edge of AGENTS.md #6's "no
  speculative abstraction."
- **N2:** `sdk/src/cli.ts` mixes 5 concerns (311 lines); `kernelDialectMarker`
  is a parse concern misplaced in the entrypoint. Watch for the next split.
- **N3:** `sdk/tests/journal-client.test.ts` (528 lines) is over the 500 smell
  threshold but pre-existing and untouched by this PR.
- **N4:** process-artifact volume dwarfs source volume in the diff; not a
  code-structure defect.

REVIEW_PASSED
