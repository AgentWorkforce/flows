## 3. Blocking findings

### F1 (P0) — the `bin` this PR ships is inert when invoked through a symlink: `flows check` exits 0, silently, on a flow it must refuse

**Where:** `sdk/src/cli.ts:280-282`, enabled by `sdk/package.json:8-10`
(`"bin": {"flows": "./dist/cli.js"}`) and `sdk/package-lock.json:11-13`.

```ts
if (process.argv[1] !== undefined && pathToFileURL(process.argv[1]).href === import.meta.url) {
  process.exitCode = runCli(process.argv.slice(2));
}
```

npm installs a `bin` as a **symlink** in `node_modules/.bin`. Node sets
`process.argv[1]` to the path as invoked (the symlink); the ESM loader resolves
`import.meta.url` through `realpath`. They never match, the guard is false, and
the process falls off the end of the module having done nothing.

**Reproduced on this tree, independently of the maintainability transcript:**

```
$ ln -s "$PWD/sdk/dist/cli.js" /tmp/binlink/flows
$ /tmp/binlink/flows check testdata/preflight/cli-missing.flow.yaml
$ echo $?
0
```

No stdout, no stderr, exit 0 — for the fixture whose entire purpose is
`REFUSED [cli_missing]`, exit 2. The same fixture through
`node sdk/dist/cli.js` refuses correctly, so the defect is invisible to every
way this repo currently exercises the code.

**Why this is blocking and not a nit:**

1. It is the precise failure mode covenant 2 exists to abolish. RFC-0001 §1:
   *"a raw stack trace, a silent wrong-workspace run, or a 'succeeded' that did
   nothing is by definition a kernel bug"* — and the cited dogfood evidence is
   *"a cron trigger reported `succeeded` into a void."* A preflight gate that
   exits 0 having checked nothing **is** that defect, shipped inside the tool
   built to prevent it. `ops/RUN-CONTRACT.md` §4 states the same rule in one
   line: *"A 'succeeded' that did nothing is a bug."*
2. It fails AGENTS.md rule 4 (**Fail closed**) at the outermost boundary: every
   refusal kind in `failure-kinds.ts` is unreachable for an installed consumer.
3. `ops/DRIVE-LOG.md:446` asserts *"The SDK now ships the `flows check`
   binary."* On the installed path it ships a binary that does nothing — a
   document asserting what the code does not do, in the package whose entire
   purpose is evidence integrity.
4. Gate 1's second done-when clause is *"`flows check` refuses the ladder flows
   when a declared CLI is missing or unauthenticated or a trigger has no
   executor."* Through the shipped entrypoint, it does not refuse anything.

**Remedy:** resolve `process.argv[1]` through `realpathSync` before
`pathToFileURL`, guarded for the absent-`argv[1]` case; then one test that
spawns the built artifact **through a symlink** and asserts exit 2 +
`REFUSED [cli_missing]`.

## 4. Non-blocking findings, each independently verified on this tree

### F4 (P2) — a CLI killed by a signal is refused as `cli_unauthenticated`, with a message that is factually false

**Where:** `sdk/src/cli.ts:189-195`; message at `sdk/src/preflight.ts:143-151`.

`probeCli` treats `result.error !== undefined` as `probe_failed` and everything
else as `authenticated: result.status === 0`. A child killed by a signal sets
neither: Node returns `{status: null, signal: 'SIGSEGV', error: undefined}`.
Verified with a fixture that `kill -SEGV $$` on `auth status`:

```
REFUSED [cli_unauthenticated] Step "a" declares CLI "./crashing-cli", but
"./crashing-cli auth status" exited non-zero; authenticate it or implement that
probe to return exit 0 when authenticated.
```

It did not exit non-zero — it did not exit. `probe_failed`, which exists for
exactly "could not verify", is bypassed, and the operator is told to
authenticate a crashing binary. Under covenant 2 the taxonomy's value is that
each kind means one thing.

**Remedy:** `if (result.error !== undefined || result.signal !== null) throw` —
one clause on the line that already exists.

### F5 (P2) — `probe_failed` is unreachable from the resolution half of the probe, contradicting the contract this PR just documented

**Where:** `sdk/src/cli.ts:208-209` (`resolveExecutable` returns `undefined`
whenever `spawnSync('which', …).status !== 0`, ignoring `.error`).

`docs/SURFACE.md:80` — added by this PR — promises *"a probe that cannot be
executed at all is `probe_failed`."* Verified false for bare-name resolution:

```
$ env PATH= node sdk/dist/cli.js check b3.flow.yaml
REFUSED [cli_missing] Step "a" declares CLI "git", but it is missing.
```

`git` is installed at `/usr/bin/git`. The probe could not be executed at all and
the operator was sent to install something already installed. F4 and F5 are the
same class from opposite ends: the two spawn sites have different error
contracts and only one is honest.

### F6 (P2 — NEW, not raised by any prior lens) — `flows check` executes a flow-declared binary with the caller's full ambient environment, and this is nowhere disclosed

**Where:** `sdk/src/cli.ts:189-193` (`spawnSync(executable, ['auth','status'], {cwd, stdio:'ignore', timeout})` — no `env` option, so `process.env` is inherited wholesale).

Verified: a flow declaring `cli: ./envleak-cli` caused `flows check` to execute
that repo-relative script, which read `$MY_TEST_SECRET` from the checking
process's environment:

```
$ MY_TEST_SECRET=super-sensitive node sdk/dist/cli.js check env.flow.yaml
RESOLVED step "a" cli "./envleak-cli" from step
CHECK PASSED env.flow.yaml
$ cat env.log
SAW_SECRET=super-sensitive
```

Running an untrusted flow spec through `flows check` is therefore arbitrary code
execution under the checker's ambient credentials. This matters beyond hygiene:
RFC-0001 gate 8's stated direction is credentials *"resolved through the proxy …
no ambient env inheritance"*, and gate 9 explicitly contemplates
**self-authored** flow specs passing *"the same verification gates"* — i.e.
`flows check` will be pointed at specs an agent wrote. `docs/SURFACE.md:80`
describes the probe as a health check and says nothing about what it executes or
with what environment.

Not blocking for gate 1 (probing auth necessarily runs the CLI), but it must be
**declared** — covenant 2 is about stating what a run can do before it does it.
Minimum: a sentence in the Preflightable-CLI contract. Better: an explicit
allowlisted `env` for the probe, filed as gate-8 work.

### F7 (P2) — `docs/SURFACE.md:78` asserts `flows check` prints five things; four of them do not exist

`emitReport` (`sdk/src/cli.ts:227-242`) prints diagnostics,
`RESOLVED step … cli … from <source>`, and `CHECK PASSED`. There is no identity,
no `<flow>/agent` derivation, no workspace scopes, no budget, no tools anywhere
in `cli.ts`. `cli` is one noun out of five.

The overclaim predates this PR, but this PR **rewrote that clause** and
surrounded it with genuinely scrupulous caveats (the unimplemented
platform-default rung, the `run.start` bypass). Tightening the neighbourhood of
a false clause makes the false clause more credible. `f0abdd4` touched this file
again and left it. This is covenant 1's "error messages and docs in the author's
vocabulary" failing in the honest direction it can least afford.

### F8 (P3) — the auth probe runs once per step, not once per CLI

**Where:** `sdk/src/preflight.ts:68-84` — probing happens inside the per-step
loop with no memoisation. Verified: a 3-step flow sharing one flow-level `cli`
produced **3** `auth status` subprocesses; a 20-step flow produces 20, each with
a 10s ceiling (`sdk/src/cli.ts:192`). Against a rate-limited auth endpoint this
makes `flows check` intermittently emit a *refusal* for a healthy CLI — a flaky
gate is a gate people learn to bypass, which costs covenant 2 more than the bug
does. `docs/SURFACE.md:80`'s "runs exactly that probe" reads as *once*.

**Remedy:** memoise `CliProbeResult` by `(cli, source)` for one `preflight()`
call — a `Map`, entirely inside the pure module.

### F9 (P3) — the trigger half of covenant 2 is a string-membership test against a file the flow author writes, documented nowhere

**Where:** `sdk/src/cli.ts:181` — `config.executors.includes(trigger.executor)`.

"A worker exists to execute every trigger" is proven by the executor's name
appearing in an array in the same `flows.json` the author edits. Nothing
contacts a registry, a broker, or RelayCron. That is a defensible **gate-1**
scope decision; what is not defensible is that it is invisible. This PR added
two substantial `SURFACE.md` paragraphs for the CLI half and zero for the
trigger half; the `flows.json` schema (`cli`, `executors`, nothing else,
fail-closed on unknown keys — `cli.ts:145-153`) is written down nowhere, and
`no_executor` is undocumented. A reader who knows RFC gate 2's
liveness-checked trigger plane will reasonably assume preflight consulted
something authoritative. Gate 2 is next.

### F10 (P3) — a stale source citation inside the evidence record itself

`ops/BACKLOG.md:74` cites `kernel/relayflowd-core/src/spec.rs:39-40` for the
`#[serde(default)] pub steps` declaration. On this tree line 39 is
`pub triggers: Vec<TriggerSpec>,` and `pub steps` is at **line 41** — the
`triggers`/`cli` fields this same PR inserted shifted it. Trivial in isolation;
noted because this package exists to eliminate exactly this class (a measured
claim in the gate record that stopped being true) and because the same commit
range is what corrected V1.

### F11 (P3, process) — the DoD was amended, by its author, in response to the review that judged it

`a5e58d7` ("ops(wp6): correct product review binding guards") rewrote
`ops/NEXT.md` DoD item 4 after the history lens's H1 showed the original guards
were mutually unsatisfiable (`a8c9110..HEAD` was required to be empty *and* the
mandated V3 edit made it non-empty).

I verified the substance: the original was logically impossible, the replacement
is correct, and the three replacement guards genuinely pass. I am not calling

amended mid-round, and the amendment is not itself reviewed. It should be
called out in the PR body as a package amendment, with the H1 transcript cited
as its cause, so the record reads as "reviewer forced a correction" rather than
"the bar moved."

## 7. Verdict rationale

The WP-6 repair work is done correctly and honestly: V1, V2 and V3 are closed,
the guards pass, history is intact, the gates are green at the numbers claimed,
and the PR body reports its own failing swarm without softening it. If WP-6 were
judged only as a documentation-repair package, it would pass.

It cannot be, because the instruction is to review `git diff main` — the whole
PR — and that diff ships a `bin` entrypoint that, invoked the way the
`package.json` declares it will be invoked, exits 0 having checked nothing. That
is covenant 2's canonical defect reproduced inside the tool written to abolish
it, it is untested by construction, and it is unrepaired at HEAD by the
package's own scope rule. The branch's newest aggregate verdict says the same
thing, and I verified it rather than inheriting it.

Two of the three lenses that last looked at this head rejected it; one of those
rejections is repaired and one is not. This review adds one further verified
finding no lens raised (F6) and confirms four carried ones by execution.

**REVIEW_FAILED**

Recommended next package: allow `sdk/src/cli.ts` + `sdk/tests/` edits, fix F1
(realpath the main-module guard) with a test that spawns the built artifact
through a symlink, take F4 and F5 in the same pass (both are one clause each and
both make an already-written doc sentence true), correct F7's overclaim and F10's
citation, and only then re-run the swarm. F6 needs at minimum a disclosure
sentence in the same edit; the scoped-env fix is gate-8 work.
