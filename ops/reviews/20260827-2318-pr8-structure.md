## The kernel boundary — the critical lens

### No product logic entered the kernel

`spec.rs` adds `cli: Option<String>` and `triggers: Vec<TriggerSpec>` to `RunSpec`, plus `cli` on the `Llm`/`Agent` step kinds, plus `TriggerSpec { id, executor }`. Every addition is **inert data + shape validation**, and the code says so at the point of contact:

- `spec.rs:33` — *"The kernel treats this as inert data; `run.start` does not invoke the surface preflight in gate 1."*
- `spec.rs:38` — *"Inert gate-1 declarations. Matching and dispatch belong to gate 2."*

The kernel validates **shape only** (empty cli, invalid/duplicate trigger, empty step cli) and stops. It does **not** resolve binaries, probe `auth status`, contact a registry, or dispatch. Verified: the kernel diff contains zero `spawn`/`process`/`fs`/`net`/`provider`/`tenant` references. This is exactly RFC §4 — *"The kernel never holds provider SDKs — LLM calls and agent execution happen SDK-side or in routed sandboxes"* — and AGENTS.md §2 — *"No provider SDKs, no product logic, no tenant awareness, no I/O in core logic."*

### Helpers over primitives — no new kernel verb

RFC decision #13 fixes the kernel vocabulary: three step verbs (`run`/`llm`/`agent`) + four resident verbs (`on`/`human`/`dispatch`/done). This PR adds **no verb**:

- `cli` is a **field** on the existing `Llm`/`Agent` step kinds, not a step type. Deterministic steps correctly omit it (`StepKind::Deterministic => &None`).
- `triggers: Vec<TriggerSpec>` is **declaration data** on `RunSpec`, not a resident verb. The resident verb is `on`; `triggers` is the data `on` compiles to. The kernel carries it the same way it carries `budget` — inert, journaled for provenance/attribution, not executed.

No primitive was added where a helper would do. The shape matches RFC §1's ladder vocabulary (`deterministic` / `llm` / `agent`).

### Closed vocabulary preserved

- `TriggerSpec` carries `#[serde(deny_unknown_fields)]`.
- Step unknown-field rejection (`STEP_LLM_FIELDS`/`STEP_AGENT_FIELDS`) was updated to include `cli` — a misspelled `cli` key is rejected, not silently dropped.
- New `SpecError` variants (`EmptyCli`, `InvalidTrigger`, `DuplicateTrigger`, `EmptyStepCli`) extend the **closed** error enum; the kernel does not invent ad-hoc strings.

### Fail-closed + completionReason discipline

Every new validation is an **error, not a warning** (fail-closed, AGENTS.md rule 4). The kernel test `preflight_data_is_fail_closed` (`spec/tests.rs`) pins all four new failure paths. The machine test `every_failed_run_terminates_with_declared_completion_reasons` (`machine/tests.rs:65`) walks eight `CompletionReason` variants and asserts each terminates the run's journal with a declared enum value — directly pinning the completionReason discipline AGENTS.md rule 4 and RFC covenant 2 demand. Tests pin deterministic code (rule 5) — satisfied.

## The SDK surface — correct layering

### Pure logic / I/O separation

`preflight.ts` (283 lines) performs **no I/O**. Environment facts arrive through the injected `PreflightProbes` interface (`cli`, `executor`, `command`), and the module's docstring states the contract: *"Environment facts are injected; this module performs no I/O."* All `spawnSync`/`which`/`readFileSync`/`accessSync` lives in `cli.ts`, which assembles `systemProbes()` and injects them. This is the right cut: preflight predicates are pure and unit-tested with fake probes; the CLI is the I/O host. The boundary is explicit, not accidental.

### Closed taxonomy, one source of truth

`failure-kinds.ts` (43 lines) defines `PREFLIGHT_FAILURE_KINDS`, `CHECK_INPUT_FAILURE_KINDS`, and `PREFLIGHT_WARNING_KINDS` as `as const` arrays with derived types and a type guard. `preflight.ts` and `cli.ts` both consume it — **one source of truth, no drift**. Covenant 2 ("typed failure ... a closed set of declared kinds") is made structural rather than aspirational. `flows check` distinguishes **refusals** (cli_missing / cli_unauthenticated / cli_unresolved / no_executor / probe_failed) from **warnings** (unprovable_effects / command_unresolved / command_unprovable), and a deterministic step always leaves exactly one warning — silence is not a state. The `warnOnUnprovableEffects` docstring justifies *why* it warns rather than refuses (a bare word may be a shell builtin under `/bin/sh -c`), keeping covenant 2's "refuses *or* warns" honest without inventing false certainty.

### Boundary dialect compiler

`compile.ts` adds `kernelToAuthoring` — the inverse of `toKernelSpec` (snake_case boundary ↔ camelCase authoring). Both translation directions belong in the compiler module; single purpose is maintained. Inbound kernel specs are fail-closed via `assertKernelKeys`/`requireKernelObject` (`CompileError` on any unknown key), so a kernel-only value with no authoring representation is refused, not silently mapped. `cli.ts`'s `kernelDialectMarker` routes a document through this inverse only when boundary-dialect markers are present, then falls back to authoring validation — the two-dialect design from SURFACE.md §"Two dialects, one journal" implemented faithfully.

## Coupling — defense in depth, not duplication

The kernel `spec.rs` and SDK `validate.ts` both validate trigger/cli shape. This is **not duplication**: they enforce the same closed-vocabulary invariants at **two different dialect boundaries** (snake_case kernel protocol vs camelCase authoring). The kernel is the last-resort fail-closed gate — Rust, structurally unable to absorb product logic (RFC §4: *"a binary you call over a protocol cannot absorb product logic; the language boundary enforces the architectural boundary"*). The SDK gives friendlier authoring-time errors. The SDK additionally does the **liveness** preflight (CLI existence + auth health) that the kernel explicitly declines to do — the spec.rs comments say so, `preflight.ts` implements it. Clean separation: **kernel validates shape; surface validates liveness.**
