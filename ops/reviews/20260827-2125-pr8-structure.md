## Findings against the constitution

### 1. Kernel stays small and pure — PASS
The kernel additions are **inert data + validation, no I/O**. `RunSpec` gains
`cli: Option<String>` and `triggers: Vec<TriggerSpec>`; the field doc-comments
state plainly that the kernel treats them as inert and that `run.start` does not
invoke surface preflight (`spec.rs:32-39`). No `std::process`, no provider SDK,
no tenant awareness, no trigger matching/dispatch was added. The actual preflight
semantics — probing `<cli> auth status`, checking executor registration — live
entirely in the SDK. This is exactly AGENTS.md rule 2 and RFC §4 ("the kernel
never holds provider SDKs"). **No product logic entered the kernel.**

### 2. No primitive added; preflight is a helper — PASS
RFC settled decision #13 fixes the kernel language at three step verbs + four
resident verbs. This PR adds **zero new step types and zero new kernel verbs**.
`TriggerSpec` is `{id, executor}` data for gate 2, not a trigger primitive.
Preflight is implemented as a **surface helper** (`preflight.ts`) whose
environment facts are **injected** (`PreflightProbes`), so the pure evaluator
performs no I/O — the RFC §3 "plugin/helper shape": contributes preflight, cannot
touch the kernel. The closed refusal taxonomy (`failure-kinds.ts`) is a surface
enum, not a kernel enum. **Helpers over primitives: respected.**

### 3. Fail-closed discipline — PASS
Kernel `spec.rs`: empty/whitespace `cli`, empty trigger `id`/`executor`,
duplicate trigger ids, and empty step `cli` all return typed `SpecError`s
(`EmptyCli`, `InvalidTrigger`, `DuplicateTrigger`, `EmptyStepCli`).
`TriggerSpec` carries `#[serde(deny_unknown_fields)]`, consistent with the
file's existing fail-closed-on-unknown-fields posture. SDK `validate.ts` rejects
unknown keys with author-vocabulary suggestions and refuses empty steps. Probe
failures classify into `probe_failed` with a non-secret detail rather than
guessing health. **No silent fallbacks introduced.**

### 4. completionReason discipline — PASS
`machine/tests.rs` adds `every_failed_run_terminates_with_declared_completion_reasons`,
which enumerates **all eight** failure `CompletionReason` variants, forces each
through `completion_actions`, deserializes the appended `StepCompletedPayload`,
and proves the run terminates in a typed `RunCompletedPayload` with
`RunCompletionReason::StepFailed`. This directly pins RFC §1 / Appendix A rule 6
("completion pins the end state … `completionReason`") and AGENTS.md rule 4.
The test is the right shape: it would fail if a new failure reason stopped
routing to a typed terminal entry.

### 5. File size — PASS (two near the line)
All source files are under the AGENTS.md rule-1 smell line (500):
largest kernel `.rs` is `server.rs` at 468; largest SDK source is `validate.ts`
at 454. No file breaches. (See observations O1/O2 for the two worth watching.)

### 6. Boundary shape matches RFC-0001 — PASS
The journal protocol remains the boundary: the SDK compiles authoring → the one
kernel dialect (`toKernelSpec`), parity is pinned by `spec-parity.test.ts` /
`spec_parity.rs`, and `cli`/`triggers` ride the same boundary artifact rather
than reaching around it. The authoring surface narrows `steps: []` while the
kernel accepts it; this asymmetry is **disclosed in `docs/SURFACE.md`** as a
chosen authoring-time narrowing and filed in `ops/BACKLOG.md` (observation O3).

## Observations (non-blocking)

**O1 — `sdk/src/cli.ts` has a wide purpose (311 lines, ~7 concerns).**
It mixes arg parsing, flow read+compile, project-config discovery (`findConfig`
walk-to-root), probe wiring (`systemProbes`/`probeCli`/`resolveExecutable`/
`classifySpawnFailure`/`executableExists`), report emission, dialect-marker
detection (`kernelDialectMarker`), and the module-invocation guard. It is well
under the 500-line line, so it is not a rule-1 breach, but it is the file most
clearly carrying more than one purpose. The probe-wiring + config-discovery
(~90 lines, `readProjectConfig`/`findConfig`/`systemProbes`/`probeCli`/
`resolveExecutable`/`classifySpawnFailure`/`executableExists`) is a natural
separate module — it is the I/O layer for preflight and has no dependency on
arg parsing or report emission. Splitting it would also let `preflight.ts`'s
injected-probe contract be tested against the real system probes in isolation.
Recommended next refactor, not a gate.

**O2 — `validate.ts` (454) and `compile.ts` (408) are near the smell line.**
`validate.ts` is cohesive (one `Validator`) but at 454 is the closest file to
500; further gate fields will push it over. `compile.ts` carries two separable
directions — forward `toKernelSpec` and reverse `kernelToAuthoring` + its
helpers (~lines 171-322). Both are defensible today; both are the files to split
first when the next rung adds fields.

**O3 — `steps: []` check/kernel asymmetry is real, disclosed, and degenerate.**
`RunSpec::validate` has no empty-steps guard (`spec.rs:84-128` loops no-op on
empty and returns `Ok(())`), so a direct `run.start` with `steps: []` is
accepted by the kernel while `flows check` refuses it as `invalid_spec`. This is
the same surface-narrows-kernel pattern as `cli` resolution, it is honestly
documented in `docs/SURFACE.md`, and a zero-step flow is meaningless — so it is
non-blocking. The clean close (already in `ops/BACKLOG.md`) is to either refuse
empty steps in the kernel too, or keep the narrowing and stop calling it a
guarantee. Naming it so the boundary stays honest.

**O4 — `cli`/`triggers` are surface concepts carried on the kernel spec.**
The kernel does not act on `cli`; it carries the string for the surface's
preflight benefit. This is a mild boundary-carrier smell (the kernel spec
becomes a transport for a surface concern), but it is defensible: it is inert,
it matches how `budget` is "carried and journaled from gate 1, enforced later,"
and fragmenting the composable unit into a separate preflight manifest would be
worse. Acceptable; noted so the carrier list does not grow silently.

## Out-of-lens note (process, not code)
`ops/DRIVE-LOG.md` grew by ~1,283 lines this PR. It is a record, not a module,
so it does not count against rule 1 — but it is becoming the repo's largest
single file by far, and append-only growth will eventually make it slow to read
and diff. A future housekeeping tick (segment-per-day, or an archive) would help
the humans who follow this repo; not a structure-gate concern.

## Summary
The kernel boundary is held: inert data only, no I/O, no provider SDK, no new
primitives, no product logic. Preflight is a surface helper with injected probes
— the helpers-over-primitives shape RFC §3/§13 asks for. Fail-closed is
enforced on both sides of the boundary, and a new enumerating test pins
completionReason discipline for every failure kind. All source files are under
the 500-line line. The four observations are refactor-next / honesty notes
(`cli.ts` purpose width, two near-threshold SDK files, the disclosed `steps: []`
asymmetry, surface concepts carried as inert kernel data); none of them puts
product logic in the kernel, adds a primitive, or grows a file past its purpose.

REVIEW_PASSED
