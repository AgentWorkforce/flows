## Shape vs RFC-0001 / AGENTS.md — each axis held

### Kernel stays pure (AGENTS.md rule 2; RFC §4) — PASS

The only kernel changes are in `spec.rs` (+`spec/tests.rs`, +`machine/tests.rs`).
What was added:

- `RunSpec.cli: Option<String>` and `RunSpec.triggers: Vec<TriggerSpec>` — both
  commented as **inert data**: `cli` is "a declaration; `run.start` does not
  invoke the surface preflight in gate 1" (`spec.rs:32-34`); `triggers` is
  "inert gate-1 declarations. Matching and dispatch belong to gate 2"
  (`spec.rs:37-38`).
- A new `TriggerSpec { id, executor }` struct with `#[serde(deny_unknown_fields)]`
  (`spec.rs:336-341`) — data, not a primitive.
- Structural validation only: non-empty `cli`/`executor`/`id`, no duplicate
  trigger ids (`spec.rs:69-81`). The kernel does **not** resolve, match,
  dispatch, or probe anything. No provider SDK, no tenant awareness, no I/O,
  no clock dependency. The new code is pure spec-shape logic on `Value`s.

No product logic entered the kernel. The preflight that *acts* on `cli`/`triggers`
lives entirely surface-side (`sdk/src/preflight.ts`).

### Closed kernel vocabulary (AGENTS.md rule 7; RFC decision #13) — PASS

The seven-word kernel language (`run`/`llm`/`agent` + `on`/`human`/`dispatch`/done`)
is untouched. Step kinds remain exactly `Deterministic | Llm | Agent`
(`spec.rs:232`). `cli` and `triggers` are **fields on the spec, not verbs** —
they add no step type and no kernel operation. This is the right reading of
"closed vocabulary": the kernel may carry new *declarative data* it journals and
hashes, without growing its *operational* vocabulary. No primitive was added.

### Helpers over primitives (RFC §1; SURFACE.md §2.3) — PASS

`flows check` preflight is a **surface helper**, not a kernel primitive. The
cleanest structural property in the PR is in `sdk/src/preflight.ts`:

- `preflight()` performs **no I/O**. Every environment fact is injected through
  the `PreflightProbes` interface (`preflight.ts:25-30`): `cli(cli, source)`,
  `executor(trigger)`, `command(binary)`. Pure predicates over a `FlowSpec`.
- All filesystem/process I/O (`probeCli` via `spawnSync`, `resolveExecutable`,
  `executableExists`, `which`, `findConfig` walking to the root) is isolated in
  `sdk/src/cli.ts:178-214`. The pure/IO split is exact and testable.

This mirrors the kernel's "no I/O in core logic" ethos on the SDK side and is
the structural opposite of the old 11,560-line runner that "resolved Slack
channel IDs" in-engine (RFC §4).

### Fail-closed (AGENTS.md rule 4) — PASS, on both sides

- **Kernel:** `RunSpec::parse` rejects unknown step fields explicitly
  (`reject_unknown_step_fields`, `spec.rs:154-179`) because `#[serde(flatten)]`
  disables serde-level `deny_unknown_fields` for steps; every non-flattened
  struct carries `deny_unknown_fields` (incl. the new `TriggerSpec`). New test
  `preflight_data_is_fail_closed` (`spec/tests.rs:120-172`) proves an unknown
  `worker` key on a trigger is rejected, empty `cli`/`executor`/`id` and
  duplicate trigger ids each return a typed `SpecError`.
- **SDK:** `validate.ts` fails closed on unknown keys at every object level with
  nearest-key suggestions (`checkKeys` + `nearestKey`/`levenshtein`,
  `validate.ts:76-86,401-436`). The closed refusal taxonomy is a single 43-line
  module (`failure-kinds.ts`) — `PREFLIGHT_FAILURE_KINDS`,
  `CHECK_INPUT_FAILURE_KINDS`, `PREFLIGHT_WARNING_KINDS` as `as const` tuples
  with a type guard. Covenant 2's "refuses *or warns* on anything it cannot
  prove" is enforced structurally: a deterministic step always leaves exactly
  one warning (`warnOnUnprovableEffects`, `preflight.ts:191-232`) — silence is
  not a permitted state.

### completionReason discipline (RFC covenant 2; AGENTS.md rule 4) — PASS

New test `every_failed_run_terminates_with_declared_completion_reasons`
(`machine/tests.rs:65-104`) iterates all eight `CompletionReason` failure
variants, asserts each produces a `StepCompletedPayload` carrying that reason,
and that the run then terminates in a `RunCompletedPayload` with
`RunCompletionReason::StepFailed`. This is the structural pin for "every
completion carries a `completionReason`" and "a raw stack trace … is by
definition a kernel bug." It directly serves gate 1's done-when. Strong.

### Boundaries (AGENTS.md rule 3) — PASS

The spec dialect is the SDK↔kernel boundary, and it is singular. `compile.ts`
maps authoring (camelCase, tagged verification sugar) → kernel dialect
(snake_case, flat v0 verification, materialized defaults) via `toKernelSpec`,
and back via `kernelToAuthoring`. Parity is **pinned by tests on both sides**
(`sdk/tests/spec-parity.test.ts`, kernel `tests/spec_parity.rs`) against shared
`testdata/`. The kernel's `SPEC_VERSION = "0.1.0"` and the SDK's
`SPEC_SCHEMA_VERSION = "0.1.0"` are checked for **equality, not shape**
(`validate.ts:100-104`), closing the false-green/false-red class. Nothing
reaches around the protocol.

## Observations (non-blocking — named for the structure record, not failures)

### O1 — the allowed-key sets are triplicated; sync is test-pinned, not construction-enforced

The "allowed keys per step type" knowledge exists in three places with three
spellings:

1. `kernel/.../spec.rs:136-152` — `STEP_COMMON_FIELDS`, `STEP_DETERMINISTIC_FIELDS`,
   `STEP_LLM_FIELDS`, `STEP_AGENT_FIELDS` (snake_case).
2. `sdk/src/validate.ts:44-61` — `ROOT_KEYS`, `STEP_COMMON_KEYS`,
   `STEP_TYPE_KEYS`, `VERIFICATION_KEYS`, `SURFACES_KEYS`, … (camelCase).
3. `sdk/src/compile.ts:189-204` — the inline `unionKeys`/`commonKeys`/`typeKeys`
   lists inside `kernelStepToAuthoring` (snake_case, the inverse direction).

Drift between any two is caught only by `spec-parity.test.ts` +
`tests/spec_parity.rs`, not by a shared constant. This is the deliberate cost of
dual independent validation (kernel is boundary of truth, SDK validates for
authoring ergonomics) and is defensible — but it is the single most likely place
for a future structural defect: the next field added to one list and not the
others passes until a parity test catches it. Worth a comment in each file
pointing at the parity tests as the sync gate, so the triplication reads as
intentional rather than accidental.

### O2 — `cli.ts` mixes orchestration, I/O, and compile-concern dialect detection

`cli.ts` (282 lines) holds four concerns: arg parsing, flow reading, project
config discovery, and report emission are all CLI orchestration and belong here.
But two pieces do not:

- **I/O probes** (`systemProbes`, `probeCli`, `resolveExecutable`,
  `executableExists`, `findConfig`, `cli.ts:162-214`) — ~53 lines of
  fs/process work. This is the only I/O in the SDK surface and it is correctly
  isolated *from* `preflight.ts`, but it lives inside the CLI entrypoint rather
  than a dedicated `probes.ts` / `io.ts`. Not a size problem today; a cohesion
  smell if `flows run`/`flows build` later want to reuse the same probes.
- **Kernel-dialect marker detection** (`kernelDialectMarker` +
  `firstPresentKey`, `cli.ts:244-270`) — this is compile/dialect *knowledge*
  (it knows `depends_on`, `max_iterations`, `retry`, `timeout_ms`,
  `recovery_mode`, `max_tokens_in`, `output_contains`, `file_globs`, … are
  kernel-dialect markers). It couples the CLI entrypoint to the kernel's
  internal key names and duplicates the key vocabulary a fourth time (see O1).
  It reads like it belongs in `compile.ts` beside `kernelToAuthoring`, with the
  CLI just calling `detectDialect(value)`.

No rule violation (under 500, concerns are sequential), but this is the file
most likely to bloat and cross-couple when gates 2/7 add dispatch paths.

### O3 — `validate.ts` (454) and `spec.rs` (452) sit closest to the 500-line smell line

Both currently hold a single purpose and are justified. But both are exactly
the files that gates 2–8 will keep adding fields to (triggers already landed in
`spec.rs`; `validate.ts` grew the trigger/surfaces/permissions validators this
PR). At the current rate `spec.rs` crosses 500 within ~2 more field families.
Pre-emptive splits to watch: in `validate.ts`, the `levenshtein`/`nearestKey`
key-suggest helpers (`validate.ts:401-436`) are a self-contained ~35-line
concern that could exit to a `suggest.ts` without touching the `Validator`
class; in `spec.rs`, the retry-default free functions (`spec.rs:405-419`) and
the `visit` cycle helper (`spec.rs:181-199`) are similarly extractable. Not
needed now — named so the line is watched, not crossed silently.

### O4 — `cli` is surface vocabulary carried as a named, validated kernel field

`RunSpec.cli` and the per-step `cli` on `Llm`/`Agent` are inert data in the
kernel, and the kernel only structurally validates non-emptiness
(`EmptyCli`/`EmptyStepCli`) — it does not resolve or dispatch on `cli`. That
keeps it within the "carried as data" allowance and is fine for gate 1. The
observation is forward-looking: `cli` is the one field in the kernel spec whose
*name* belongs to the authoring/agent-runner surface, not the kernel's
operational vocabulary. As gates 2 and 7 land, the structural invariant to hold
is that the kernel never starts *acting* on `cli` (resolving a binary, choosing
a sandbox) — that stays surface-side. If it ever does, `cli` should become an
opaque declaration the kernel hands back to the surface, not a field the kernel
interprets. Worth a one-line comment on `RunSpec.cli` stating that intent, since
today's comment only says "inert in gate 1."

## Verdict

Through the structure lens the PR is sound. The kernel took on **inert
declarative data and structural validation only** — no product logic, no I/O,
no new primitive, no widening of the seven-word vocabulary. Preflight is a
surface helper with a clean pure/IO split. Fail-closed parsing holds on both
sides and is test-pinned, including a new test that pins `completionReason`
discipline across all failure kinds. The boundary is the spec dialect, parity
is test-pinned both ways, and every product source file is under the 500-line
line with a single purpose. Both rails (not on `main`; gate not self-judged)
hold.

O1–O4 are watch items and minor cohesion notes, not violations: nothing puts
product logic in the kernel, nothing adds a primitive instead of a helper, and
no file has grown past its purpose. None blocks merge on structural grounds.

**REVIEW_PASSED**
