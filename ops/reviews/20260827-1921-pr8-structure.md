## What is structurally clean

### 1. The kernel stayed pure — `cli` and `triggers` are inert boundary data

AGENTS.md rule 2 / RFC §4: the kernel holds journal, scheduler, leases, timers, streams —
no provider SDKs, no product logic, no tenant awareness, no I/O, simulated clock. The two
new `RunSpec` fields pass that test:

- **`cli: Option<String>`** (`spec.rs:34-35`, on `Llm`/`Agent` at `:242,:247`) is an
  *inert preflight declaration*. The kernel carries it across the boundary and validates
  only non-emptiness (`EmptyCli`/`EmptyStepCli`). It does not resolve, spawn, or probe it
  — preflight does, SDK-side (`preflight.ts:106-115`, `cli.ts:181-191`). The doc comments
  on both sides state this verbatim (`spec.rs:32-33`, `spec.ts:126-127,:139-140`). The
  kernel's `validate` additions are pure shape checks with no I/O. ✓
- **`triggers: Vec<TriggerSpec>`** (`spec.rs:37-38`) is *inert gate-1 data*. The comment
  (`spec.rs:36-37`, `spec.ts:148-149`) declares "Matching and dispatch belong to gate 2."
  The kernel validates shape only (non-empty `id`/`executor`, no dupes) — no
  `EventFrameV1`, no matching, no dispatch, no liveness. ✓

No trigger matching, no dispatch, no provider call, no permission enforcement, no live
model/agent invocation was added anywhere in `kernel/**`. The simulated-clock contract is
untouched. The language boundary continues to enforce the architectural boundary.

### 2. No primitive was added — helpers/declarations over verbs (RFC decision #13)

RFC decision #13: the kernel vocabulary is closed at three step verbs (`run`/`llm`/`agent`)
+ four resident verbs. Gate 6 deletes the `integration` primitive; integrations compile to
mount writes. This PR adds **no verb**. Step types remain exactly
`deterministic | llm | agent` (rule 7), confirmed in `spec.rs:269-273`, `spec.ts:13`,
`validate.ts:26-30`. `cli` and `triggers` are *fields on existing types*, surface data
that compiles across the boundary — precisely decision #13's "surface compiles to kernel
primitives." `TriggerSpec` is minimal `{id, executor}` with no speculative fields. ✓

### 3. Fail-closed discipline extended symmetrically (AGENTS.md rule 4; RFC covenant 2)

- `#[serde(deny_unknown_fields)]` on `RunSpec`, `TriggerSpec`, and every nested struct;
  `STEP_LLM_FIELDS`/`STEP_AGENT_FIELDS` widened for `cli` so the hand-rolled unknown-field
  rejector stays exhaustive (`spec.rs:144-151`). A guessed `worker:` key on a trigger is
  rejected at parse — pinned by `preflight_data_is_fail_closed` (`spec/tests.rs`).
- Four new typed `SpecError` variants (`EmptyCli`, `InvalidTrigger`, `DuplicateTrigger`,
  `EmptyStepCli`) — every kernel refusal is a declared kind, never a raw error.
- SDK side: `PREFLIGHT_FAILURE_KINDS` / `CHECK_FAILURE_KINDS` are `as const`, gated by
  `isCheckFailureKind`; every exit-2 path constructs a `CheckFailure` with a declared kind;
  the catch-all maps an unexpected throw to `invalid_spec` rather than leaking a stack
  trace (`cli.ts:83-88`). No `console.warn` where an error belongs.
- Probes fail closed: a throwing probe → `probe_failed` *refusal*
  (`preflight.ts:125-133,:162-170`); a hung CLI (`result.error`) throws → refusal, not
  assumed healthy (`cli.ts:189`). A CLI lacking `auth status` exits non-zero →
  `cli_unauthenticated` (refused, not assumed). ✓

### 4. `completionReason` discipline strengthened (RFC Appendix A; AGENTS.md rule 4)

`every_failed_run_terminates_with_declared_completion_reasons`
(`machine/tests.rs:65-104`) enumerates all eight non-`Success` `CompletionReason`
variants, feeds each through `completion_actions`, and asserts the run terminates in typed
`RunCompletionReason::StepFailed` with a deserializable closed payload. This pins the
covenant-2 "closed failure taxonomy" at the kernel and extends Appendix A's
exactly-once-effects reasoning to the terminal-journal shape. ✓

### 5. Probes are injected — the SDK preflight is I/O-free and deterministic

`PreflightProbes` is an injected interface (`preflight.ts:25-30`); `preflight()` performs
no I/O. `systemProbes` (`cli.ts:173-179`) is the only place subprocesses happen, and it is
the CLI's concern, not the preflight evaluator's. This mirrors the kernel's "no I/O in
core logic" ethos on the SDK side and makes induced faults hermetic (fixture executables,
not `PATH` mutation). ✓

### 6. The dialect bijection is co-located and testable (F5 closure)

`kernelToAuthoring` and its inverse `toKernelSpec` now both live in `compile.ts` and are
exported (`compile.ts:146,:171`), with a round-trip parity test. The earlier structural
defect — a private inverse in `cli.ts` that was unreachable from tests — is closed. ✓

### 7. No dead code / no speculative abstraction (AGENTS.md rule 6)

Every `failure-kinds.ts` constant is consumed by `preflight.ts`, `cli.ts`, or a test. The
three orphaned fixtures found during F2 work were wired into `cli.test.ts` rather than
left dead. The dead `args.at(-1)` branch (F5) and the dead `delete flow['cli']` mutation
(R5) are gone. `TriggerSpec` carries only what gate-1 preflight needs. ✓

## Observations — non-blocking, for the gates that inherit this code

### O1 — `triggers`/`executor` is gate-2 vocabulary now named inside the kernel spec

The kernel's closed *verb* set is intact, but the kernel's `RunSpec` now *names* a gate-2
concept (`TriggerSpec`, `executor`). Carrying it inertly across the boundary is defensible
— the compiled spec is the boundary contract (decision #9: "data, schema-validated,
diffable"), and the comments explicitly fence it as inert. It is not a violation. It is,
however, the thin end of a wedge: gate 2 must not read this presence as license to push
trigger matching or dispatch into the kernel. The fence today is a doc comment and
discipline; structurally it would be stronger if the kernel's `triggers` field were
documented as "validated for shape, never read by the scheduler" right at the field, and if
gate 2's matching lives in `relayflowd`'s *server* layer (which already has the event
router) rather than in `relayflowd-core`. Naming it so the next gate inherits the boundary,
not the field.

### O2 — Two independent validators that canonical-fixture parity does not keep in agreement

This is the most important structural risk, and it is live. There are two spec validators
that must agree:

- `kernel/relayflowd-core/src/spec.rs::RunSpec::validate` (Rust)
- `sdk/src/validate.ts::validateSpec` (TypeScript)

plus a third decision point, `cli.ts::isKernelSpec` (dialect detection).

The parity suites (`spec_parity.rs`, `spec-parity.test.ts`) pin **compiled canonical
artifacts**, not **validation behavior**. A spec that is valid to one validator and
invalid to the other is not necessarily caught by canonical-fixture parity — and the PR's
own backlog (P2, genuine and unfixed) proves it: the SDK accepted `version: 9.9.9` that the
kernel rejects, and the SDK required `name` that the kernel treats as optional. Round-4
(N3) found a third manifestation: `isKernelSpec`'s heuristic misroutes a kernel-valid spec
omitting both `depends_on` and `max_iterations` through the authoring compiler, which then
rejects it for snake_case keys.

This is the intentional cost of the Rust/TS boundary (RFC §4). It is honestly filed and
correctly out of gate 1's done-when. A structure review names it because **the closed
failure-taxonomy covenant (covenant 2) has a seam here that canonical-fixture parity does
not cover**: a false-green from `flows check` lets a run start that the kernel refuses,
which is the minute-27 failure class preflight exists to close. The durable structural fix
is a shared *validation-behavior* contract — a corpus of `(spec, accepts | rejects,
which-side)` cases both validators must agree on — not only shared canonical fixtures.
Recommend the next gate grow that corpus alongside the canonical pins.

### O3 — `spec.rs` (451) and `validate.ts` (454) are one gate away from the 500-line smell

AGENTS.md rule 1: "any file approaching 500 lines is a design smell; justify it or split
it." Measured on the current tree, four files sit in the 451–468 band
(`server.rs` 468, `server/session.rs` 465, `journal/lib.rs` 451, `spec.rs` 451, plus
`validate.ts` 454). Nothing crosses 500. Two grew on this PR:

- **`spec.rs` (451)** is single-purpose (spec) but does four things: type definitions,
  `validate`, `reject_unknown_step_fields`, and the `visit` cycle detector. It is the file
  most likely to cross 500 when gate 2 adds trigger matching or gate 6 adds mount fields.
- **`validate.ts` (454)** is single-purpose (validation) but carries the
  `nearestKey`/`levenshtein` suggestion helpers (~40 lines, `:401-436`) — a separable
  concern (error-message ergonomics, not validation logic).

Both are defensible today. The structural recommendation is to split *before* the next
gate grows them — type-defs vs. validation in `spec.rs`, and the suggestion helpers out of
`validate.ts` — rather than after they cross 500.

### O4 — The completionReason test is exhaustive by inspection, not by the compiler

`machine/tests.rs:65-104` enumerates the eight failure `CompletionReason`s in a hand-written
array. A ninth variant added later will not fail this test; the closure is honorary, not
structural. A `match` the compiler checks for exhaustiveness (or an enum-iteration derive)
would make the taxonomy-closure guarantee match the discipline it asserts. Non-blocking;
the guarantee holds today.

### O5 — `cli.ts` is a small grab-bag; its dialect heuristic is the weakest structural point

`cli.ts` (272) packs arg parsing, flow reading, project-config discovery (`findConfig`
upward walk), probe wiring, dialect detection (`isKernelSpec`), subprocess resolution, and
report emission. Each function is small and it is well under 500, but the concerns are
separable. `isKernelSpec` (`cli.ts:239-256`) — inferring dialect from the presence of
optional snake_case keys — is the structurally weakest piece and the source of the N3
misroute (O2). A `$schema`/version discriminator or explicit flag would be more durable
than a heuristic, but it changes the compiled-spec format (a pinned gate-1 artifact), so
it is correctly out of scope here. Filed so gate 2/6 do not inherit the heuristic as
permanent.

### O6 — `flows check` executes a binary the spec names (trust boundary unstated)

`probeCli` (`cli.ts:181-191`) spawns `<cli> auth status`, with a path-shaped `cli`
resolved relative to the flow file's directory. Proving "auth health" without invoking the
CLI is not possible (RFC §34), so the execution is justified — but neither `SURFACE.md`
nor the CLI output states the trust boundary: checking an untrusted `.flow.yaml` runs code
shipped alongside it. Before the checker is exposed to third-party flows (gate 6 / plugins,
RFC §211), this should be a documented boundary. Round-4 (N4) raised this; it remains
undocumented.
