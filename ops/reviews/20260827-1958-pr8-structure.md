## Findings against the lens

### 1. Kernel boundary holds — inert data, not product logic (PASS)

AGENTS.md rule 2/3 and RFC §4: the kernel holds journal/scheduler/leases/timers,
no provider SDKs, no product logic, no I/O. The new `cli` and `triggers` fields
are **carried as inert data** across the SDK↔kernel boundary, not acted on:

- `spec.rs:32-38` documents the intent inline: *"The kernel treats this as inert
  data; `run.start` does not invoke the surface preflight in gate 1."* and
  *"Inert gate-1 declarations. Matching and dispatch belong to gate 2."*
- Verified by search: `.cli` and `.triggers` are referenced **only** in
  `spec.rs` (validation) and `spec/tests.rs` (tests). No execution path in
  `engine.rs`, `machine.rs`, `state.rs`, `server.rs`, or the journal crate reads
  them. The kernel never resolves a CLI, never matches a trigger, never calls a
  provider.

This is the correct split: the kernel owns the spec's serialized shape (so it can
journal, hash, and replay it — RFC settled decision #5/#14), the surface owns the
semantics (preflight probes now, dispatch in gate 2). It mirrors how `budget`,
`surfaces`, and `permissions` are already carried as inert gate-1 data in the same
file. Consistent and closed.

### 2. No primitive added — `TriggerSpec` is data, not a verb (PASS)

RFC settled decision #13: the kernel vocabulary is closed — three step verbs
(`run`/`llm`/`agent`) + four resident verbs (`on`/`human`/`dispatch`/`done`).
The review brief asks me to flag anything that "adds a primitive instead of a
helper." `TriggerSpec` is **not a kernel primitive**: it is a two-field data
struct (`id`, `executor`) embedded in `RunSpec`, validated for shape only. It
adds no step verb, no resident verb, no journal entry type, no scheduler hook. The
resident verb `on` (triggers) is explicitly deferred to gate 2 in the comment. No
`@relayflows/adapter-*`, no integration primitive (gate 6's deletion target is
respected). ✓

### 3. Fail-closed discipline holds on both sides of the boundary (PASS)

AGENTS.md rule 4 / RFC covenant 2.
- Kernel parse is fail-closed: `deny_unknown_fields` on every non-flattened
  struct; explicit `reject_unknown_step_fields` for the `#[serde(flatten)]` step
  objects; the four new `SpecError` variants refuse rather than coerce an empty
  `cli`, an empty/duplicate trigger id, or an empty executor.
- SDK `validate.ts` fails closed on unknown keys at every object level and names
  the nearest valid key in the author's vocabulary (`did you mean "dependsOn"?`).
- `preflight.ts` deterministic-command path leaves **exactly one** warning in
  every knowable state (`unprovable_effects` / `command_unresolved` /
  `command_unprovable`); silence is not a state. The earlier F1 fail-open (silent
  on an unresolvable command) is genuinely closed — the `catch` block now emits
  `command_unprovable`, and the resolved-but-unknown-effects and unresolved cases
  are both diagnosed.

### 4. `completionReason` taxonomy is closed and pinned (PASS)

RFC §1 / Appendix A / AGENTS.md rule 4 require every completion to carry a typed
`completionReason` and the failure set to be closed.
- `CompletionReason` (`entry.rs:159`) is a closed 9-variant enum (Success + 8
  failures); `RunCompletionReason` (`entry.rs:376`) is a closed 4-variant enum.
- The new `machine/tests.rs` test `every_failed_run_terminates_with_declared_completion_reasons`
  enumerates all 8 failure reasons, asserts each failed step appends a
  `StepCompletedPayload` carrying that exact reason, and asserts the run
  terminates in `RunCompletedPayload` with `RunCompletionReason::StepFailed`.
  This is exactly the "tests pin deterministic code" discipline AGENTS.md rule 5
  demands, and it pins the closed-set invariant the covenant requires.

### 5. File size & single purpose (PASS, with one watch item)

AGENTS.md rule 1: ~500 lines is a design smell. Measured on the shipped tree
(`find … | xargs wc -l`, excluding `target/`):

| File | Lines |
|---|---|
| `kernel/relayflowd/src/server.rs` | 468 |
| `kernel/relayflowd/src/server/session.rs` | 465 |

| `kernel/relayflowd-journal/src/lib.rs` | 451 |
| `sdk/src/validate.ts` | 454 |

Nothing reaches 500. Single-purpose discipline is clean: `spec.ts` = types,
`validate.ts` = validation, `compile.ts` = authoring↔kernel mapping, `preflight.ts`
= pure predicates, `failure-kinds.ts` = closed taxonomy, `cli.ts` = I/O + args +
report. The kernel change is purely additive to `spec.rs` + tests; `machine.rs`,
`state.rs`, `entry.rs` were not touched, so coupling did not grow.

**Observation O1 (non-blocking, watch):** `sdk/src/validate.ts` (454) is the
largest SDK file and is a single `Validator` class covering the whole schema. It
is cohesive and under cap, but it is the file most likely to cross 500 as gates 6
(integration helpers) and 8 (permissions) deepen the schema. A pre-emptive split
(`validate/triggers.ts`, `validate/steps.ts`) before it crosses 500 would be
cheaper than after. Not a finding against this PR.

## Non-blocking observations (named, not blockers)

- **O2 — `kernelDialectMarker` is shape-sniffing, not an explicit tag.**
  `cli.ts:244-266` decides whether input is authoring or kernel dialect by
  scanning for snake_case keys (`depends_on`, `max_iterations`, `retry`, …). The
  code itself comments that a document with no marker is *ambiguous* and is
  validated as authoring. For gate-1 surface ergonomics this is defensible, but
  it couples the CLI to both dialects' key shapes and will surprise an author
  whose camelCase field accidentally collides. The boundary would be cleaner with
  an explicit dialect marker (a field or a separate subcommand). Structural smell,
  not a defect; out of scope for a preflight PR.

- **O3 — `compile.ts` now carries both directions of the bijection plus
  canonicalization plus retry-default assertions (408).** Cohesive (all
  spec-shape mapping) and the F5 move (inverse next to its `toKernelSpec`) is
  correct — the two halves of one bijection belong in one module, exported, and
  the round trip is pinned by `spec-parity.test.ts`. If it grows further, the
  kernel-dialect key-assertion helpers (`requireKernelObject`,
  `assertKernelKeys`, `kernelStepToAuthoring`) are a natural sibling
  `kernel-dialect.ts`. Watch item, not a finding.

- **O4 — the DRIVE-LOG's "structural gate" verbatim block is stale against the
  shipped tree (record hygiene, not code structure).** The log quotes
  `370 sdk/src/cli.ts` / `2385 total`, but the actual tree measures
  `282 sdk/src/cli.ts` / `2480 total`, and the logged top-2 omits `compile.ts`
  (408) and `journal-client.ts` (351). The *code's* actual sizes are all under
  500, so the structural cap holds — but the self-reported structural evidence in
  the PR record is inaccurate and is quoted as "verbatim." This is a provenance
  problem in the log, not a structural problem in the code; flagging because a
  structure reviewer should not accept quoted numbers at face value, and here
  they do not reproduce.

## Summary

The kernel remains small, pure, and closed: the new `cli`/`triggers` fields are
inert carried data with no execution-path readers, no provider SDK, no I/O, no
new verb. The preflight lives entirely on the surface, with I/O injected so the
predicates stay pure. The failure taxonomy is a closed enum set, pinned by a test
that enumerates every failure reason. No file reaches the 500-line cap; the
largest (server.rs 468, validate.ts 454) are under it. No primitive was added
where a helper/data field would do. The shape matches RFC-0001 and AGENTS.md.
The three observations (validate.ts size to watch, dialect-sniffing heuristic,
stale log numbers) are non-blocking and none of them is a structural defect in
the shipped code.

REVIEW_PASSED
