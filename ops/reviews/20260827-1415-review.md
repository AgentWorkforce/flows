## 3. Findings

### P1-1 — `relayflowd resume` on a worker-less parked run hangs 30 s then dies with a raw error (regression)

`kernel/relayflowd/src/engine/drive.rs:43-45`

The no-compatible-worker branch changed the registry status from `"parked"` (the deleted code at old `engine.rs:~236`) to `"waiting_worker"`. `kernel/relayflowd/src/server.rs:457-468` — untouched by this diff — treats `waiting_worker` as "an out-of-band worker is mid-attempt", polls for 30 seconds, and then:

```rust
anyhow::bail!("timed out waiting for out-of-band completion of run {run_id}")
```

Reproduced against the built binary with a live `serve` and **no worker attached**:

```
# agent step
$ relayflowd --data-dir /tmp/rf-review/data resume 01M126PVFCHKYKKEG6DD76HVX8
Error: timed out waiting for out-of-band completion of run 01M126PVFCHKYKKEG6DD76HVX8
resume exit=1  elapsed=30s

# llm step — the rung-(b) path that shipped green in PR #4
$ relayflowd --data-dir /tmp/rf-review/data resume 01M126R433SHS80WX4FQR6S4XA
Error: timed out waiting for out-of-band completion of run 01M126R433SHS80WX4FQR6S4XA
resume exit=1  elapsed=30s
```

Before this change both returned `{"status":"parked", ...}` immediately, exit 0. Nothing is coming — no worker
is attached and no lease exists — so the status is a lie and the CLI failure is a raw error, not a declared kind
(covenant 2). The new test `agent_without_a_compatible_worker_parks_waiting_worker_without_starting`
(`server/tests.rs:362-390`) asserts the registry row directly and never goes through `resume_via_socket`, so
the regression is invisible to the suite.

Either keep `"parked"` for "no worker exists" and reserve `"waiting_worker"` for "a worker holds a lease"
(note `park_idle_run`, `drive.rs:188-194`, already makes exactly that distinction), or teach
`resume_via_socket` to distinguish the two.

### P1-2 — two agent steps on different workspace surfaces wedge the run with an `internal` error

`kernel/relayflowd/src/engine.rs:243-249` + `engine.rs:271-305`, `kernel/relayflowd-core/src/machine.rs:148-150`

`start_actions` gives a later agent step's attempt `state.current_pins` — the *previous* step's end pins.
`prepare_start_entry` only asks the dispatcher for fresh pins when `current_pins.is_none()`, then runs
`validate_agent_pins`, which requires the pin set to exactly equal *this* step's declared surfaces. So a flow
whose second agent step declares a different surface can never start. Reproduced:

```
run.start:  {"ok":true,"result":{"run_id":"01M126VB5VCRXR457RNESDTP82","status":"parked"}}
step.complete (edit):
  {"ok":false,"error":{"code":"internal",
   "message":"agent step doc pins do not cover its declared workspace and stream surfaces"}}
```

Journal of that run, terminal state:

```
1|run.spawned||
2|step.attempt.started|edit|1
3|step.completed|edit|1        <- no run.completed, ever
```

Registry status stays `waiting_worker`; `resume` re-parks (exit 0, `completed_steps: 1`) and re-bails the moment
a worker attaches. The run is permanently unrunnable and terminates in no declared failure kind.

Appendix A rule 6 chains pins *per surface*; it does not say step N+1 must declare the same surface set as
step N. This conflates "the run's current pins" with "this step's declared surfaces" — and it is exactly the
shape gate 3's discover→implement→review DAG will need. The DoD claims "End-pin chaining: a step's start pins
equal the previous completion's `end_pins`"; the only test for it
(`state/tests.rs:74`) uses two steps that both declare `repo`, so the heterogeneous case is unexercised.

### P1-3 — an agent worker that attaches without pins bricks the run at `run.start`

`kernel/relayflowd/src/server/wire.rs:55-56` (`pins` is `#[serde(default)]`), `session.rs:290-334`, `engine.rs:246-248`

`worker.attach` accepts a worker declaring `step_types: ["agent"]` with no `pins`. The failure surfaces later,
when a step is about to start:

```
attach:    {"id":"a1","ok":true,"result":{"worker_id":"nopins"}}
run.start: {"id":"s1","ok":false,
            "error":{"code":"internal","message":"worker nopins omitted revision for surface repo"}}
```

and the run is left at registry status `running` with no terminal entry:

```
01M126SWBM03W7B9Q8XCR22AEW|running
```

This is covenant 2's preflight case verbatim — pin coverage is provable at attach time, and instead it fails
after the run has started, as an untyped `internal` error, leaving a run stuck in `running` that nothing will
ever drive. Reject the attach (or park the step with a declared kind) rather than erroring mid-drive.

### P2-4 — the agent-completion validation failure is swallowed

`kernel/relayflowd/src/engine/remote.rs:60-63`

```rust
if validate_agent_completion(&step, runtime, &completion, &recorded).is_err() {
    failure_reason = Some(CompletionReason::WorkerError);
}
```

`validate_agent_completion` distinguishes five distinct causes (no journaled start pins, omitted
`started_pins`, pin mismatch, `end_pins` failing surface coverage, effects disagreeing with journaled facts).
All five collapse to a bare `worker_error` and the message is dropped on the floor — the journal keeps the
worker's own `output` and no diagnostic. Contrast `exec_det::worker_error(detail)`
(`exec_det.rs:114-124`), which journals `{"error": detail}`. AGENTS.md rule 4 ("no silent fallbacks, no
`console.warn` where an error belongs") and covenant 1 (errors name the mistake in the author's vocabulary).
Journal the detail in the completion `output`.

### P2-5 — `manual` mode's `diff_ref` is a hardcoded placeholder

`kernel/relayflowd-core/src/machine.rs:406`

```rust
diff_ref: Some("pinned-revision..current".to_owned()),
```

Appendix A rule 4 requires the park to carry "a diff of pinned revision vs. current state". The human gets a
constant string containing neither the pinned revision id nor the surface. The pinned revision is right there
in `runtime.last_start_pins`. Same for the fixed prompt "An agent attempt crashed with a dirty workspace" —
it doesn't name the step or run.

### P2-6 — `llm` completions journal unvalidated, undeclared effects

`kernel/relayflowd/src/server.rs:239` + `remote.rs:57-66` (else-branch)

`step.complete` previously hardcoded `effects: Vec::new()`. Agent completions now cross-check the claimed
effects against journaled `effect.recorded` facts — good. But the non-agent branch passes `completion.effects`
straight through. An `llm` step declares no surfaces at all, so any effect it claims is undeclared (Appendix A
rule 1: "anything undeclared is outside the contract") and unbacked by a journaled fact (rule 3). Reject
non-empty `effects` on non-agent completions.

### P3-7 — `trajectory_tail` is documented "bounded" and is not bounded

`kernel/DESIGN.md:71`, `kernel/relayflowd-core/src/entry.rs:185-188` ("Bounded worker-supplied execution
context"). Nothing anywhere bounds it. It is arbitrary worker-supplied JSON, journaled, held in `StepRuntime`
(`state.rs:58`), and re-decoded on every `RunState::fold`. Either enforce a byte cap at
`server.rs:241` or drop the word "bounded" from both the doc and the comment.

### P3-8 — the new epoch pin reconstruction is dead on arrival and lossy

`kernel/relayflowd-core/src/state.rs:349-366` rebuilds `current_pins` from
`EpochSummaryPayload::pinned_revisions`. Every producer writes that map **empty** —
`relayflowd-journal/src/lib.rs:359` and `relayflowd-core/src/journal.rs:136` — and `rollover` has no
production caller (only the scaffolding test). So the branch always yields `None`, and if it were ever
populated it would drop `streams: Vec::new()`, breaking the very pin chain P1-2 enforces. AGENTS.md rule 6
("no dead code, no speculative abstraction"). Either populate the writer side and pin it with a test, or leave
the reader out until epochs are real.

### P3-9 — pins and dispatch can select different workers

`session.rs:290-296` (`starting_pins`) and `session.rs:338-344` (`dispatch`) each take the session lock
separately and each pick "the first worker handling this step type". With two agent workers attached, or a
detach between the two calls, the journaled pins can come from a worker other than the one that receives the
dispatch — a silently wrong starting state, which is exactly the class Appendix A exists to close. Resolve the
worker once and pass it through.

### P3-10 — record-before-perform makes effects at-most-once, not exactly-once

`remote.rs:176-215` + `tests/crash_resume/agent_support.rs:145-173`. A crash between the `effect.recorded`
append and the provider call permanently suppresses the effect: the next attempt reads `deduped: true` and
skips, so the provider sees **zero** calls while the journal claims the effect happened. Appendix A rule 5's
"one provider call" holds; "the effect occurs" does not. `ops/NEXT.md` explicitly prescribed this shape
("records a writeback *before* performing it … so a second attempt's provider call is suppressed rather than
merely detected afterwards"), so this is a consequence of the plan, not a deviation from it — but it is the
gap between v0's split record/perform and Appendix A rule 3's "the mount write **is** the effect record", and
it should be stated in the PR body rather than left for a reader to discover.
