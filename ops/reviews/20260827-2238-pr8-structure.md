## Findings

### F1 — Kernel stays pure; `cli`/`triggers` are inert data, not product logic (PASS)

AGENTS.md #2 and RFC §4 forbid provider SDKs, product logic, tenant awareness, and I/O in the
kernel. Verified against the working tree:

- `rg tenant kernel/` → no matches. No `tenant_id` anywhere. (RFC decision #15 holds.)
- `rg 'spawn|process|reqwest|http|tokio||std::net|std::fs::canonicalize'` over
  `kernel/relayflowd-core/src/` (non-test) → only the `run.spawned` journal-entry name and a
  comment in `machine/recovery.rs`. `lib.rs:3` still states the crate "deliberately contains no
  filesystem, process, network, SQLite."

The new kernel fields (`spec.rs:32-39`, `spec.rs:243/248`) carry `cli: Option<String>` and
`triggers: Vec<TriggerSpec>` as **inert data**. The kernel validates them *structurally* only —
non-empty (`EmptyCli`, `EmptyStepCli`, `InvalidTrigger`), no duplicate ids
(`DuplicateTrigger`) — exactly the pattern already used for step ids, `max_iterations`, and
`RetryPolicy`. No spawn, no `auth status`, no worker lookup. The comments at `spec.rs:32-37`
say so explicitly: *"The kernel treats this as inert data; `run.start` does not invoke the
surface preflight in gate 1."* and *"Matching and dispatch belong to gate 2."*

The actual preflight (CLI existence + auth probe, executor registration probe) lives in the
**surface**: `sdk/src/preflight.ts`, with all I/O behind the injected `PreflightProbes`
interface (`preflight.ts:36-46`: *"this module performs no I/O"*). That is the correct layering
per RFC gate 1 (`flows check` refuses/warns) and gate 2 (triggers are entry conditions, not
kernel schedulers).

### F2 — Closed kernel vocabulary preserved; no primitive added (PASS)

RFC decision #13: the kernel language is three step verbs (`run`/`llm`/`agent`) + four resident
verbs (`on`/`human`/`dispatch`/`done`); everything else is surface that compiles to kernel
primitives. AGENTS.md #7: step types are exactly `deterministic | llm | agent`.

- `StepKind` is still `Deterministic | Llm | Agent` (`spec.rs:232-259`); `StepType` still the
  same three (`spec.rs:268-274`). No new step verb.
- `cli` is a **field** on `Llm`/`Agent`, not a verb. `triggers` maps to the `on` resident verb
  (decision #13 lists `on` as kernel vocabulary), so carrying trigger declarations in the spec
  is well-grounded — the kernel owns the resident verb; gate 2 does the matching/dispatch.
- No new primitive was added where a helper would do. Preflight is a **helper** (`preflight()`
  in the SDK) with a closed taxonomy in its own 43-line module (`failure-kinds.ts`), not a
  kernel primitive. This is the helpers-over-primitives discipline (RFC gate 6's "no
  `integration` primitive" is the same principle; this PR doesn't touch integrations).

### F3 — Journal-protocol boundary is pinned by parity tests (PASS)

The SDK↔kernel boundary is one dialect, enforced both ways:

- `spec-parity.test.ts` now round-trips authoring↔kernel
  (`kernelToAuthoring(toKernelSpec(flow))`), normalizes empty `triggers: []` to match kernel
  serialization exactly (stable hash), and **refuses** a kernel retry policy the authoring
  dialect can't represent (`expect(...).toThrow('retry.initial_backoff_ms')`) — fail-closed on
  the inverse mapping, never a silent drop.
- The compiler marks authoring sugar the kernel dialect can't carry as a `CompileError`
  (`compile.ts:144`), and `requireNoTimeout` rejects `timeoutMs` on llm/agent (`compile.ts:381`).
- Both sides share `testdata/` fixtures; `compileYamlToCanonicalJson` == kernel canonical JSON.

Nothing reaches around the protocol.

### F4 — `completionReason` discipline is pinned, not narrated (PASS)

`machine/tests.rs` adds `every_failed_run_terminates_with_declared_completion_reasons`: it
iterates the closed `CompletionReason` enum (`VerificationFailed`, `RetriesExhausted`,
`LeaseExpired`, `Crashed`, `Timeout`, `WorkerError`, `BudgetExceeded`, `Canceled`), asserts each
failed step completion carries the typed reason, AND asserts the run terminates with a declared
`RunCompletionReason::StepFailed`. This is AGENTS.md #4 (every completion carries a
`completionReason`) and RFC covenant 2 (typed failure, no raw stack trace) made into a gate.
The closed refusal taxonomy on the surface side (`failure-kinds.ts`) is a separate concern
(preflight refusals before a run starts) and is also closed + type-guarded.

### F5 — File size & single purpose: all under 500, two approaching it (WATCH)

AGENTS.md #1: 500 lines is a design smell; justify or split. No file crosses it. Every module
is single-purpose (spec types / compile / validate / preflight / taxonomy / CLI entry). Two
files are within ~10% of the line and deserve a named split target before the next rung lands:

- **`sdk/src/validate.ts` (454).** One more step-type or surface kind pushes it over. The
  `nearestKey`/`levenshtein` suggestion block (~lines 401-436) and the predicates (440-454) are
  general-purpose helpers unrelated to the per-type validation; they are the natural extract
  into a `validate-helpers.ts`. Not a violation today.
- **`kernel/relayflowd-core/src/spec.rs` (452).** The `validate()` body
  (`spec.rs:64-129`) is accumulating one structural validator per declaration family
  (cli, triggers, steps, retry, deps, cycles). If another declaration family lands, split the
  per-family validators (trigger/cli/retry) into helpers so `validate()` reads as a sequence of
  delegations. Not a violation today.

### F6 — `cli` in the kernel spec is a coupling seam to watch (WATCH, non-blocking)

`triggers` is well-grounded (`on` is a kernel resident verb, F2). **`cli` is the weaker one:**
it has no kernel runtime role — the kernel never resolves or invokes a CLI (the surface
preflight does, and llm/agent dispatch is SDK-side/sandbox). It is carried in the kernel spec
for provenance/journal-legibility and so the surface preflight, running over the same spec, has
the data. This is defensible under RFC decision #14 (the sealed bundle includes "the flow's
preflight declaration") and the inertness comments are honest.

The structural risk is drift: if `cli` ever gains a kernel runtime role — the kernel resolving
CLIs, checking auth, or branching on the value — it crosses the "no product logic / no I/O in
the kernel" line (AGENTS.md #2) and becomes a surface concern living in the kernel. **Today it
does not cross.** Recommendation: keep `cli` strictly inert in the kernel; the moment the kernel
needs to act on it, move it to a sidecar preflight-declaration section of the bundle rather
than a field on `RunSpec`/`StepKind`. Naming the seam now so the split is obvious when it's
needed.

### Non-code structural note (not a finding)

`ops/reviews/` carries 39 `*pr8*` artifacts from this one PR. Read as clutter it looks like a
smell; read against RFC §2.7 it is the intended design — a review swarm of distinct-lens
relayflows firing per PR, each emitting its own artifact. Not a structural defect; called out
only so a future reader doesn't mistake the volume for accretion.

## Summary

The shape matches RFC-0001 and AGENTS.md. The kernel is small and pure (no tenant, no I/O, no
SDK, no product logic); the new `cli`/`triggers` are inert data with structural-only
validation, and the real preflight is a surface helper with injected probes. The closed kernel
vocabulary is intact (no new verb/primitive). The journal-protocol boundary is pinned both ways
by parity tests, and `completionReason` discipline is pinned by a closed-enum test. No file
crosses 500 lines and every module is single-purpose. Two watch items (F5 file-size approach,
F6 `cli`-in-kernel coupling seam) are named for the next rung; neither blocks.
