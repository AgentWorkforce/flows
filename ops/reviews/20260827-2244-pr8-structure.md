## 1. Kernel purity — no product logic in the kernel  (PASS)

AGENTS.md §2: the kernel holds journal/scheduler/leases/timers/streams; no
provider SDKs, no product logic, no I/O, tenant-unaware, simulated clock.

The only kernel change is `spec.rs`. It adds `cli: Option<String>` to `RunSpec`
and to the `StepKind::Llm`/`StepKind::Agent` variants, and `triggers:
Vec<TriggerSpec>`, each annotated as **inert**:

- `RunSpec.cli` doc: "The kernel treats this as inert data; `run.start` does
  not invoke the surface preflight in gate 1." (`spec.rs:93-97`)
- `RunSpec.triggers` doc: "Inert gate-1 declarations. Matching and dispatch
  belong to gate 2." (`spec.rs:98-100`)

The kernel's only behavior on these fields is schema validation that fails
closed (`EmptyCli`, `InvalidTrigger`, `DuplicateTrigger`, `EmptyStepCli` at
`spec.rs:428-436`; `TriggerSpec` carries `#[serde(deny_unknown_fields)]` at
`spec.rs:174-179`). No dispatch, no CLI invocation, no probe, no provider call.

Verified by search — there is **no** use of the new fields anywhere in the
kernel outside the spec module and its tests:

```
$ rg -n '\.cli|triggers|TriggerSpec' kernel/ --type rust \
    -g '!**/spec.rs' -g '!**/spec/tests.rs' -g '!**/machine/tests.rs'
NO USES OUTSIDE SPEC/MACHINE-TESTS
```

The fields are carried so the canonical boundary artifact (RFC decision #14 —
content-addressed spec JSON) retains the author's declarations for hashing,
provenance, and gate-2 consumption. That is data preservation across the
boundary, not product logic. No `tenant_id`, no I/O, no SDK. **Purity holds.**

## 2. Closed kernel vocabulary — no primitive added  (PASS)

RFC decision #13: three step verbs (`run`/`llm`/`agent`) + four resident verbs
(`on`/`human`/`dispatch`/`done`) are the whole kernel language; the surface is
open, the kernel is closed.

- `cli` is a **field** on the existing `Llm` and `Agent` step variants
  (`spec.rs:239-244`, `spec.rs:246-252`), not a new step type. The three step
  verbs (`deterministic`/`llm`/`agent`) are unchanged — matching AGENTS.md
  rule 7.
- `TriggerSpec` is data for the **existing** `on` resident verb, declared inert
  for gate 1. It is not a new verb and not a new step kind.

No kernel primitive was added. The new executable behavior (resolution,
probing, refusal) is entirely surface-side.

## 3. Helpers over primitives — preflight is a pure evaluator  (PASS)

RFC §3: "the kernel is closed, the surface is open"; first-party helpers are
plugins that ship in the box. The preflight is implemented exactly as a helper,
not a primitive:

- `sdk/src/preflight.ts` is a **pure evaluator**: it takes a `FlowSpec` and an
  injected `PreflightProbes` interface (`preflight.ts:14831-14836`) and emits
  typed diagnostics. It performs **no I/O**. Verified:

  ```
  $ rg -n 'spawnSync|readFileSync|accessSync|process\.|child_process' sdk/src/preflight.ts
  NO-IO-IN-PREFLIGHT
  ```

- All environment facts (CLI existence/auth, executor registration, command
  resolution) are collected in `sdk/src/cli.ts` `systemProbes`
  (`cli.ts:14318-14324`) and injected. This keeps I/O at the boundary and makes
  preflight hermetically testable (the fixtures + `bin.test.ts` exercise the
  real binary; the unit tests inject fake probes).

- `failure-kinds.ts` (43 lines) is a small closed taxonomy — single purpose.

This is the textbook "surface helper compiles to / exercises kernel data"
shape the RFC asks for.

## 4. Fail-closed discipline  (PASS)

AGENTS.md rule 4 / RFC covenant 2: no silent fallbacks; refuse or warn on the
unprovable; every completion carries a `completionReason`.

Kernel (`spec.rs`):
- empty flow `cli` → `EmptyCli`; empty step `cli` → `EmptyStepCli`
  (`spec.rs:108-110`, `spec.rs:129-135`).
- trigger with empty `id`/`executor` → `InvalidTrigger`; duplicate `id` →
  `DuplicateTrigger` (`spec.rs:112-120`).
- `TriggerSpec` uses `#[serde(deny_unknown_fields)]` — unknown keys fail
  closed.

Surface (`validate.ts` / `cli.ts`):
- Unknown keys fail (`checkKeys`); `cli` must be non-empty; triggers validated
  for shape + duplicate ids (`validate.ts:15239-15264`).
- `spec.version` was tightened from "any semver" to **exact match against
  `SPEC_SCHEMA_VERSION`** (`validate.ts:15208-15215`) — a narrowing, fail-closed.
- `flows check` exits **2** on every refusal; `config_invalid` on unknown
  `flows.json` keys (`cli.ts:14285-14293`); `cli_unresolved` **refuses rather
  than guesses** (documented in `docs/SURFACE.md`).

Deterministic-command `command_unresolved` is a **warn, not refuse**
(`preflight.ts:15062-15067`). This is not a silent fail-open: it emits a typed
warning for every deterministic step (covenant 2's "refuses **or warns**"), and
the justification is structural — the kernel runs string commands through
`/bin/sh -c` (`kernel/relayflowd/src/exec_det.rs`), so an unresolved bare word
may be a builtin/function/assignment and refusing would reject valid flows.
The narrower path-like refusal is correctly filed in `ops/BACKLOG.md` rather
than silently dropped. Defensible; not a structural defect.

## 5. completionReason discipline  (PASS — strengthened)

The PR adds `every_failed_run_terminates_with_declared_completion_reasons`
(`kernel/relayflowd-core/src/machine/tests.rs:41-80`). It enumerates **all
eight** `CompletionReason` variants (VerificationFailed, RetriesExhausted,
LeaseExpired, Crashed, Timeout, WorkerError, BudgetExceeded, Canceled) and
proves each failed attempt appends a typed `StepCompleted` whose payload
deserializes to the closed struct with the matching reason, and that the run
then terminates in `RunCompleted` with `RunCompletionReason::StepFailed`. This
pins the closed-failure-kind invariant the RFC makes a kernel bug-by-definition
to violate. A structural strengthening, not just an additive test.

## 7. Boundaries & coupling  (PASS)

- The journal protocol remains the boundary. The SDK compiles authoring →
  `KernelRunSpec` (`compile.ts:toKernelSpec`) and now also maps kernel →
  authoring (`kernelToAuthoring`) so `flows check` can accept either dialect;
  the kernel parses `RunSpec`. The new `cli`/`triggers` fields flow consistently
  through both shapes (`KernelTriggerSpec` ↔ `TriggerSpec`).
- The surface never reaches around the journal protocol — preflight reads the
  compiled spec and probes the environment; it does not touch the journal or
  the run path. `docs/SURFACE.md` explicitly discloses that the journal client's
  direct `run.start` does **not** invoke surface preflight at gate 1 — the
  asymmetry is named, not hidden.
- `preflight.ts` couples only to `spec.ts` types and `failure-kinds.ts`. No
  kernel coupling. `cli.ts` couples to `compile.ts` + `preflight.ts` + node:fs
  — the I/O seam is isolated here by design.

## Non-blocking observations (none rises to a structural blocker)

- **O1 — `compile.ts` now hosts two directions.** It grew from compile-only to
  compile + decompile (`kernelToAuthoring`, ~160 lines, `compile.ts:14506+`),
  bringing it to 408 lines. Both directions share the dialect knowledge, so
  co-location is defensible today. If the inverse grows another rung, split
  `kernelToAuthoring` (and its `assertKernelKeys`/`requireKernelObject`
  helpers) into a `dialect-convert.ts` so the compiler stays one direction.
- **O2 — `validate.ts` is the closest file to the 500-line smell line (454).**
  Still single-purpose and cohesive. Worth monitoring as more declared fields
  land; the per-type validators (`validateLlm`/`validateAgent`/`validateTriggers`)
  are the natural split candidates if it approaches 500.
- **O3 — `cli.ts` bundles several sub-concerns** (arg parsing, `flows.json`
  parent-walk discovery, `kernelDialectMarker` detection, probe wiring, report
  emission) at 311 lines. All are cohesive to "run `flows check`," but
  `kernelDialectMarker` + the config walk are the cleanest candidates to lift
  into a small helper module if the command grows past one subcommand.
- **O4 — `triggers` is inert in the kernel by design.** It is not dead code
  (the surface preflight exercises it via `no_executor`, and the kernel
  validates it fail-closed), but a future reader may mistake the kernel-side
  non-dispatch for dead code. The `// Inert gate-1 declarations` doc comment
  already guards against this; keep it as gate 2 lights the field up.
- **O5 — diff is dominated by narrative, not code.** ~40 `ops/reviews/*` files
  and a +1,400-line `DRIVE-LOG.md` append outweigh the source change. This is
  repo-hygiene/process, outside the structure-of-code lens, but the PR's
  signal-to-noise is low; a squash-merge that drops the review-churn files (or
  keeps only the final per-lens transcripts) would leave a cleaner history.

## Verdict

No product logic entered the kernel. No primitive was added — `cli` is a field
on existing step verbs and `TriggerSpec` is data for the existing `on` verb,
both carried inert across the boundary. The new executable behavior is a
surface helper implemented as a pure evaluator with injected probes
(helpers-over-primitives, exactly the RFC §3 shape). Fail-closed holds on both
sides; `completionReason` discipline is strengthened by an exhaustive
completion-reason test. Every source file is under 500 lines, the two new
modules are single-purpose, and the journal protocol remains the boundary.

REVIEW_PASSED
