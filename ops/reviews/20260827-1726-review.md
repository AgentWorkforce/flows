**N4 — `flows check` executes a binary the spec names.**
`probeCli` (`sdk/src/cli.ts:171-181`) spawns `<cli> auth status`, with a
path-shaped `cli` resolved **relative to the flow file's directory**
(`:184-186`). Checking an untrusted `.flow.yaml` therefore runs code shipped
alongside it. This is deliberate and documented — `docs/SURFACE.md:80` states the
probe as the preflightable-CLI contract, and proving "auth health" without
invoking the CLI is not possible — but neither `SURFACE.md` nor the CLI's own
output states the trust boundary. **Recommendation:** file a note that
`flows check` is not safe on untrusted specs, before the checker is exposed to
third-party flows (gate 6 / plugins, RFC §211).

**N5 — trigger-executor proof is a declaration, not a registry.**

(`sdk/src/cli.ts:166`) — a static array in `flows.json`. RFC covenant 2 asks

and honest for gate 1, where `spec.ts` and `spec.rs` both declare triggers inert
and dispatch a gate-2 concern, and the scoreboard does not overclaim it. Flagged
so gate 2 does not inherit the list as if it were liveness. This is the same
family as Nabis's "cron trigger reported `succeeded` into a void" evidence in
