## 3. The fixes, and why each is structural

Both findings have one shape — the reader handed control of a bound to the thing
it was bounding — so both fixes move the decision back to the reader. Neither
widens a bound; the numeric limits are unchanged (10 s / 8192 B / 300 s / 1 MiB).

### P1-1 — the deadline resolves, it does not merely signal

`terminate()` cleared the only lifecycle timer, sent `SIGTERM`, armed an unref'd
`SIGKILL`, and then left resolution to `child.once('close')`. Node emits
`'close'` only after the process has exited **and** every inherited stdio stream
has closed, so any descendant holding one withholds it forever — and by then the
deadline that was supposed to bound the wait had already been cleared. There was
no deadline left in the system.

The fix arms a settle timer inside `terminate()` that calls `finish()` directly,
mirroring `spawnInvocation` (`sdk/src/worker-cli.ts:99-108`), where the timer
resolves rather than delegating to a child-controlled event:

```ts
      killTimer = setTimeout(() => child.kill('SIGKILL'), FORCE_KILL_DELAY_MS);
      killTimer.unref();
      settleTimer = setTimeout(
        () => finish(failure(message)),
        FORCE_KILL_DELAY_MS + SETTLE_AFTER_KILL_MS,
      );
```

Why structural rather than a widened bound: the previous code had **no** bound on
this path at any value — it waited on an event the producer controls, so no
timeout constant could have helped. After the fix, every path into
`executePinnedWrapper` is covered by an armed lifecycle timer at all times (the
handshake timer until `phase === 'execute'`, then the execution timer), and
every lifecycle timer routes through `terminate()`, which now guarantees
settlement within `FORCE_KILL_DELAY_MS + SETTLE_AFTER_KILL_MS`. Resolution no
longer depends on anything the wrapper can withhold.

The settle is armed *after* the `SIGKILL`, not instead of it, so a wrapper that
closes its pipes normally still resolves through `'close'` on the existing
timeline — the reviewer's `w15` control (ignores SIGTERM, leaks no pipe) still
resolves on the SIGKILL escalation. And `failure(message)` builds exactly the
result the `'close'` path builds for a set `protocolError` (`exit_code: null`,
empty stdout, the same diagnostic), so this changes **when** the session settles
and never **what** it settles to.

Deliberately not done: resolving early on `'exit'`. The process being dead does
not mean the pipe has been drained, so an exit-triggered resolution would
truncate output nondeterministically — the same class of bug as P1-2. A leaked
pipe therefore costs the full execution deadline. That is now documented.

### P1-2 — the handshake bound is measured after the buffer is drained

The 8 KiB check ran against the whole accumulated `handshakePending` **before**
the loop that drains complete lines and flips `phase` to `'execute'`. When the
execute token and the payload landed in one read, the token that would have
ended the handshake was sitting at the front of the buffer, unread, while the
size check fired against bytes that were already execution output.

The fix inverts the order: drain complete lines first; if the handshake
completed, hand the residue to `acceptExecutionData` (governed by
`maxOutputBytes`); only if the handshake is *still open* apply
`HANDSHAKE_OUTPUT_LIMIT` — and then only to the un-terminated residue, which is
the sole buffer the handshake still owns. The message now names the bound and
its value.

Why structural rather than a widened bound: raising 8192 would have moved the
cliff, not removed it, and left the outcome dependent on OS pipe coalescing. The
defect was that the wrong bytes were being measured. After the fix the handshake
bound applies only to bytes that are, by construction, handshake bytes, so the
same wrapper produces the same result whether or not its writes coalesce — which
is what the three-variant test asserts.

The handshake remains bounded in every direction. An un-terminated flood before
the handshake completes trips the residue check (verified below, 64 KB with no
newline). A flood *with* newlines is refused by `acceptHandshakeLine` on the
first non-conforming line. And once the handshake completes, the reader-side
`maxOutputBytes` takes over on arrival. Nothing can accumulate without a bound.

### P2-1 — the four bounds are documented

`docs/SURFACE.md` gains a "Declared wrapper bounds" table naming the handshake
deadline (10 s), the handshake byte limit (8192 B), the execution deadline
(300 s), and `maxOutputBytes` (1 MiB), each with what it applies to and the
refusal a wrapper author will see. It also states that the bounds are
reader-owned and that a leaked stdio pipe costs the full execution deadline.
