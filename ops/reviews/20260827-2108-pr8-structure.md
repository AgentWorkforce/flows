## 1. Boundaries — clean

The central structural question this PR raises is whether preflight (covenant
2) drags product logic into the kernel. It does not.

- **`cli` and `triggers` are inert data on the kernel spec.**
  `kernel/relayflowd-core/src/spec.rs:32-39` adds both fields to `RunSpec` with
  comments that state the contract explicitly: `cli` — "The kernel treats this
  as inert data; `run.start` does not invoke the surface preflight in gate 1.";
  `triggers` — "Inert gate-1 declarations. Matching and dispatch belong to
  gate 2." `RunSpec::validate` (`spec.rs:64-102`) checks only **structural**
  validity — non-empty strings, non-empty executor, unique trigger ids — which
  is spec-validity, the kernel half of covenant 2 ("spec validity"). It does
  **no** auth-health probe, no executor-registry contact, no PATH resolution,
  no subprocess spawn. All of that lives in the SDK.

- **The kernel vocabulary stays closed.** Step types are exactly
  `deterministic | llm | agent` (`spec.rs:232`, `StepKind`). `TriggerSpec` is
  `{id, executor}` only (`spec.rs:338-341`), `#[serde(deny_unknown_fields)]`,
  no speculative fields. No new step verb, journal verb, or kernel operation
  is introduced. This is RFC-0001 settled decision #13 ("the kernel vocabulary
  is closed; the surface is open") held intact.

- **The preflight is a surface helper.** `sdk/src/preflight.ts` is the pure
  evaluator (probes injected, no I/O — see `preflight.ts:20-30`); `sdk/src/
  cli.ts` owns the I/O half (probe execution, config discovery, report
  emission). Nothing in `kernel/` imports or knows about `flows check`. This
  matches RFC-0001 §4 ("The kernel never holds provider SDKs … LLM calls and
  agent execution happen SDK-side or in routed sandboxes") and gate 6's "no
  `integration` primitive" — preflight is a check, not a step type.

- **The dialect boundary is preserved.** `sdk/src/compile.ts` carries `cli`
  and `triggers` across the authoring↔kernel dialect as plain data
  (`compile.ts:75-78, 110, 120, 151-152, 174, 180, 191, 200-202, 224, 231,
  351, 360`), normalizing empty triggers symmetrically with the kernel's
  `skip_serializing_if = "Vec::is_empty"` (`spec.rs:38`). Parity is pinned
  bit-for-bit by both `tests/spec_parity.rs` and `sdk/tests/spec-parity.test.ts`.

## 2. Fail-closed discipline — extended symmetrically, real on both sides

- **Kernel side.** `deny_unknown_fields` on `TriggerSpec` (`spec.rs:337`);
  four new `SpecError` variants — `EmptyCli`, `EmptyStepCli`, `InvalidTrigger`,
  `DuplicateTrigger` (`spec.rs:429-438`) — all surfaced from `validate`. The
  `cli`/`triggers` validation lives in `RunSpec::validate` (`spec.rs:69-81,
  94-100`), not in a silent coerce. `reject_unknown_step_fields` was widened
  to admit `cli` on `llm`/`agent` only (`spec.rs:145-152`), so a `cli` on a
  deterministic step is a parse error, not a dropped field.

- **SDK side.** `ROOT_KEYS` and `STEP_TYPE_KEYS` extended (`validate.ts:44-51`);
  `validateTriggers` checks id uniqueness and non-empty executor
  (`validate.ts:163-188`); `validateCli` rejects empty (`validate.ts:303-307`);
  `validateSpec` refuses unsupported `version` before preflight (`validate.ts:
  100-104`). The closed refusal taxonomy lives in `sdk/src/failure-kinds.ts`
  (43 lines, single purpose): `cli_missing`, `cli_unauthenticated`,
  `cli_unresolved`, `no_executor`, `probe_failed` + input kinds. A thrown
  probe routes to `probe_failed` (`preflight.ts:129-131`), not silently
  swallowed; a signal-killed `<cli> auth status` throws → `probe_failed`
  (`cli.ts:194`), not misreported as `cli_unauthenticated`. No `console.warn`
  where an error belongs; every refusal carries a kind the operator can act on.

- **Honest asymmetry disclosed, not hidden.** The authoring surface refuses
  `steps: []` as `invalid_spec` while the kernel accepts it (`validate.ts:122`
  vs `spec.rs:40` `#[serde(default)]`). `docs/SURFACE.md` now states this is a
  deliberate authoring-time narrowing, not a kernel guarantee. That is the
  correct way to hold a boundary seam — name it, don't paper over it.

## 3. `completionReason` discipline — pinned by a new kernel test

`kernel/relayflowd-core/src/machine/tests.rs:65-104`
(`every_failed_run_terminates_with_declared_completion_reasons`) enumerates
all eight non-`Success` `CompletionReason` variants, asserts each failed step
appends a typed `StepCompletedPayload` carrying that reason, and asserts the
run terminates in typed `RunCompletionReason::StepFailed`. This is covenant
2's "typed failure … journaled with its `completionReason`" made into a gate.
It is a genuine behavior test, not a reachability assertion. (One
test-exhaustiveness note, non-blocking: the enumeration is by inspection; a
ninth `CompletionReason` variant added later would not fail this test. The
converse — no undeclared kind reaches output — is held by the typed enum at
compile time, which the test comment could state.)

## 5. Coupling — mostly clean, one disclosed heuristic

- **`preflight.ts` is decoupled.** It imports only types from `spec.ts` and
  `failure-kinds.ts` (`preflight.ts:1-5`); all environment facts arrive
  through the injected `PreflightProbes` interface. It performs no I/O. This
  is the correct split — the pure half is testable with injected faults, the
  I/O half is isolated in the entrypoint.

- **Dialect detection is by key-shape heuristic.** `kernelDialectMarker`
  (`cli.ts:245-267`) infers kernel-vs-authoring dialect by inspecting
  snake_case keys (`depends_on`, `max_iterations`, `retry`, `timeout_ms`,
  `recovery_mode`, budget/verification/permission shapes). It is fail-closed
  — every misroute I can construct rejects with `invalid_spec`, and a
  document with no marker is validated as authoring input. Structurally,
  inferring the boundary dialect by pattern-matching rather than by an
  explicit `$schema`/version discriminator is a mild coupling smell: the
  detector reconstructs the dialect from the shape of the data rather than
  reading a declared tag. It is safe today and disclosed in `docs/SURFACE.md`,
  and changing it would touch the canonical spec format (hash-pinned on both
  sides), so it is correctly out of scope for this PR. A `$schema`
  discriminator remains the more durable shape. Non-blocking.

## 6. Observations (non-blocking)

These do not put product logic in the kernel, do not add a primitive, and do
not grow a file past its purpose. They are named for the next pass.

- **O1 — `sdk/src/cli.ts` concentrates the I/O half of preflight.** At 294
  lines it is under the cap, but it holds arg parsing, flow reading, project-
  config discovery + parsing (`findConfig`, `readProjectConfig`), probe
  execution (`systemProbes`, `probeCli`, `resolveExecutable`,
  `executableExists`), dialect detection (`kernelDialectMarker`), report
  emission, and the main-module guard. The pure half is correctly in
  `preflight.ts`; the I/O half is all in `cli.ts`. Splitting the probe/config
  helpers into their own module (e.g. `sdk/src/probes.ts`) would make the I/O
  boundary explicit, keep the entrypoint to wiring, and give the spawn-and-
  probe code a single home that `bin.test.ts` can target directly. Smell, not
  violation — flagging it now because `cli.ts` is the file most visibly
  accruing a second purpose.

- **O2 — dialect-by-heuristic (see §5).** Fail-closed and disclosed; a
  `$schema`/version discriminator is the durable shape when the canonical
  format is next free to move.

- **O3 — `ops/` record volume.** The overwhelming majority of the 13k-line
  diff is `ops/` (DRIVE-LOG, NEXT, SCOREBOARD, BACKLOG, ~40 review
  transcripts). These are append-only record/reporting artifacts, not code,
  and do not affect the structure of the codebase. Noting only that the
  process record is growing fast and is itself unbounded — a future
  `ops/DRIVE-LOG.md` compaction/epoch rule (RFC settled decision #8 is the
  analog for journals) would keep it navigable. Not a code-structure concern.
