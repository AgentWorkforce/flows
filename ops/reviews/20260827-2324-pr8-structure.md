## Detailed findings

### F1 — Kernel purity: clean (no defects)

AGENTS.md rule 2 and RFC §4 require the kernel to hold no provider SDKs, no product logic, no tenant awareness, no I/O — built against a simulated clock.

The kernel changes in `spec.rs` are **pure data additions**:
- `cli: Option<String>` on `RunSpec` — a default CLI declaration, carried as inert data.
- `triggers: Vec<TriggerSpec>` — inert gate-1 declarations.
- `cli: Option<String>` on `StepKind::Llm` and `StepKind::Agent` — per-step CLI override, inert data.
- `TriggerSpec { id, executor }` — a data struct, no behavior.

The spec.rs doc comments explicitly state the boundary:
> "The kernel treats this as inert data; `run.start` does not invoke the surface preflight in gate 1."
> "Inert gate-1 declarations. Matching and dispatch belong to gate 2."

The kernel validates only that the data is well-formed (non-empty, no duplicates, fail-closed on unknown fields). It does **not** spawn processes, contact registries, or resolve paths. All preflight I/O lives in the SDK (`sdk/src/preflight.ts` with injected `PreflightProbes`, `sdk/src/cli.ts` with `systemProbes`). This is the correct separation: the language boundary enforces the architectural boundary, as RFC §4 prescribes.

No product logic in the kernel. No provider SDKs. No I/O. **Pass.**

### F2 — Journal protocol as boundary: clean

AGENTS.md rule 3 and RFC §4 require SDKs and surfaces to speak the journal protocol; nothing reaches around it.

The SDK's `compile.ts` maps the authoring shape (camelCase, tagged verification sugar) to the kernel's single boundary dialect (snake_case, flat v0 verification, defaults materialized). The reverse mapping (`kernelToAuthoring`) exists for `flows check` to read compiled kernel specs. The `spec-parity.test.ts` pins both sides to the same `testdata/` fixture, and the kernel's own `spec_parity.rs` does the same from the Rust side — making `sha256(canonical JSON) == kernel spec_hash` a tested fact.

The `KERNEL_RETRY_DEFAULTS` constant in `compile.ts` duplicates the kernel's retry defaults. This is a coupling point, but it is explicit, documented, and tested. The alternative (sharing a constants file across Rust/TS) would violate the language boundary. This is the right approach.

**Pass.**

### F3 — Fail-closed discipline: clean

AGENTS.md rule 4 requires fail-closed: no silent fallbacks, every completion carries a `completionReason`.

**Kernel:**
- `deny_unknown_fields` on every non-flattened struct.
- `reject_unknown_step_fields` explicitly checks the `#[serde(flatten)]` case that serde cannot enforce.
- New validation: empty flow CLI, empty step CLI, invalid trigger (empty id/executor), duplicate trigger id — all return typed `SpecError` variants.
- New test `preflight_data_is_fail_closed` pins the unknown-field rejection on triggers and the empty-CLI/empty-trigger validation paths.

**SDK:**
- `validate.ts` rejects unknown keys at every object level (root, budget, step, verification, surfaces, permissions, triggers) with author-vocabulary suggestions ("did you mean `dependsOn`?").
- `preflight.ts` refuses on `cli_missing`, `cli_unauthenticated`, `cli_unresolved`, `no_executor`, `probe_failed`; warns (never silent) on `unprovable_effects`, `command_unresolved`, `command_unprovable`. A deterministic step always leaves exactly one diagnostic — silence is not a state.
- `failure-kinds.ts` defines the taxonomy as `as const` arrays; the `PreflightRefusal.kind` field is typed to the union, so the compiler holds the converse (no undeclared kind can be emitted).
- Tests prove every declared kind is reachable.

**Pass.**

### F4 — completionReason discipline: clean

AGENTS.md rule 4 and RFC covenant 2 require every failure to be a declared kind, journaled with its `completionReason`.

The new kernel test `every_failed_run_terminates_with_declared_completion_reasons` (machine/tests.rs:66) iterates over all eight `CompletionReason` variants (`VerificationFailed`, `RetriesExhausted`, `LeaseExpired`, `Crashed`, `Timeout`, `WorkerError`, `BudgetExceeded`, `Canceled`), injects each as a failure, and asserts:
1. The `StepCompletedPayload` carries the exact reason.
2. The run terminates with `RunCompletionReason::StepFailed`.

This is exactly the "raw stack trace or silent success is a kernel bug" discipline from RFC covenant 2.

**Pass.**

### F5 — Helpers over primitives: clean

RFC settled decision #13: the kernel vocabulary is closed (three step verbs `run`/`llm`/`agent` + four resident verbs). Everything else is surface that compiles to kernel primitives.

No new kernel step types, verbs, or primitives are added. The `cli` and `triggers` are **data fields** on the existing `RunSpec` and `StepKind` structs, not new primitives. Preflight is a **surface helper** in the SDK, not a kernel mechanism. The closed vocabulary is untouched.

**Pass.**

### F6 — Vocabulary match: clean

AGENTS.md rule 7: step types are `deterministic`, `llm`, `agent`. Journal entries carry RFC §1 / Appendix A names.

The kernel's `StepType` enum and `StepKind` enum use exactly these names. The SDK's `StepType` type matches. `RecoveryMode` values (`reset`, `inspect`, `manual`) match Appendix A rule 4. `CompletionReason` and `RunCompletionReason` variants match the closed failure taxonomy in RFC covenant 2.

**Pass.**

### F8 — Forward-looking observations (non-blocking)

These are not defects. They are the files most likely to need attention as the ladder grows.

**O1 — `sdk/src/cli.ts` (311 lines) is an orchestration layer accumulating responsibilities.**
It currently handles: arg parsing, flow file reading, project config discovery (`findConfig` walking to root), system probe wiring (`systemProbes`), dialect detection (`kernelDialectMarker`), report emission, and the `runCli` entry point. Each function is small and focused, but the file is doing many different things. When gate 2 adds more commands (e.g., `flows run`, `flows build`), this file will need to split — likely into a `cli/` directory with `check.ts`, `config.ts`, `probes.ts`, and `dialect-detect.ts`. Not urgent at 311 lines, but it is the file to watch.

**O2 — `sdk/src/compile.ts` (408 lines) combines two cohesive but separable concerns.**
The file's own header acknowledges "Compilation is two mappings": (1) YAML → validated authoring `FlowSpec` (`compileYaml`/`compileSpec`/`compileStep`) and (2) authoring ↔ kernel dialect mapping (`toKernelSpec`/`kernelToAuthoring` + helpers). At 408 lines with clear section breaks this is acceptable, but the `kernelToAuthoring` path and its validation helpers (~130 lines, lines 171–322) could extract into a `dialect.ts` if the file grows past 450. The `KERNEL_RETRY_DEFAULTS` coupling would move with them.

**O3 — `sdk/src/validate.ts` (454 lines) is approaching the 500-line threshold.**
It is single-purpose (validation) but dense. The `nearestKey`/`levenshtein` helpers (lines 408–436, ~29 lines) are general-purpose string utilities that have no domain knowledge — they could live in a `sdk/src/util/nearest-key.ts` to give the validator breathing room. Not blocking, but the file is 46 lines from the smell threshold.

**O4 — `kernelDialectMarker` in `cli.ts` (lines 262–284) duplicates kernel field-name knowledge.**
The marker function checks for snake_case keys (`depends_on`, `max_iterations`, `retry`, `timeout_ms`, `recovery_mode`, budget keys, verification keys, permission keys) to detect whether a file is a compiled kernel spec or authoring input. This is a fragile coupling: if the kernel adds new snake_case fields, the marker list must be updated in lockstep. It is tested (cli.test.ts:248–256), and the dual-dialect design makes it necessary, but it is the most fragile coupling point in the PR. A comment or shared test that asserts the marker list matches the kernel's `STEP_*_FIELDS` constants would strengthen it.

**O5 — PR carries 60+ review artifact files and 1,549 lines of DRIVE-LOG.**
These are process metadata from the review swarm (RFC §2 rule 7), not code. They do not affect code structure, but they inflate the PR's diff footprint (17,975 insertions, of which the actual code is ~2,500 lines). This is a PR hygiene observation, not a structural defect. The review artifacts are correctly placed in `ops/reviews/` and do not contaminate `kernel/` or `sdk/`.
