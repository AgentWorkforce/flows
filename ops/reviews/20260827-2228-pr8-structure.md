## Lens

One lens only: **structure** — boundaries, coupling, file size and single
purpose, and whether the shape matches RFC-0001 (closed kernel vocabulary,

## What this PR is

PR #8 lands the **gate-1 authoring surface** as a TypeScript SDK plus a narrow
kernel-core change. The kernel diff touches exactly three files
(`+++ b/` in the diff):

- `kernel/relayflowd-core/src/spec.rs` — adds inert `cli`/`triggers` data +
  fail-closed validation

## Findings

### F1 — `sdk/tests/journal-client.test.ts` is 528 lines (low severity, file size)

AGENTS.md rule 1: "Any file approaching 500 lines is a design smell; justify it
or split it." One authored file crosses it:

```
$ wc -l sdk/tests/journal-client.test.ts
528 sdk/tests/journal-client.test.ts
```

It is 28 lines over the threshold. It appears to be a single-subject loopback
double for `JournalClient` (framing, correlation, demultiplex, fail-closed,
the 14 protocol verbs) — so it is not multi-purpose, but it is past the smell
line. **Action:** justify it in a header comment or split by verb family if it
grows further. Not blocking; no other authored file is close (next largest are
`validate.ts` 454 and `spec.rs` 452). `node_modules` is vendored and excluded.

### F2 — Dual validation layers with parity pinned on the artifact, not the rules (low severity, coupling)

There are two spec validators: the Rust `RunSpec::validate`
(`kernel/relayflowd-core/src/spec.rs:64`) and the TS `validateSpec`
(`sdk/src/validate.ts:397`). They operate on **different shapes** (authoring
camelCase vs. kernel snake_case), which is the correct layering per covenant 1
(author-side errors in author vocabulary) + covenant 2 (kernel fail-closed on
the boundary dialect). They are consistent **today** (both reject empty `cli`,
duplicate triggers, unknown fields, dependency cycles).

The parity gate, however, pins only the **compiled artifact** —
`tests/spec_parity.rs` and `tests/spec-parity.test.ts` both hash
`testdata/hello-ladder.spec.canonical.json` — not the **validation rules**. So a
future rule added to the kernel's `validate()` with no SDK counterpart would
pass `flows check` and then refuse at `run.start`: a minute-0-checkable failure
surfacing at run start, i.e. a covenant-2 regression the suite would not catch.

**Action:** consider a parity test that asserts a shared corpus of *invalid*
specs is refused by both layers with the same `kind`. Low severity because the
divergence is fail-closed (the kernel still refuses), just later than covenant 2
wants. Not blocking for this PR.

### N1 — Review-artifact churn in the tree (note, not a code-structure defect)

The diff adds ~44 files under `ops/reviews/20260827-*-pr8-*.{md}` plus
`ops/{BACKLOG,DRIVE-LOG,NEXT,SCOREBOARD}.md`. This is process output, not code,
so it is outside the structure lens — flagged only because the review swarm is
committing a high volume of its own artifacts to the working tree, which is
noise in `git log`/diffstat. No action required for a structure pass.

## Positive structural signals (verified)

**Kernel purity is provable, not asserted.** `AGENTS.md` rule 2 forbids provider
SDKs, product logic, tenant awareness, and I/O in `kernel/`; rule says built
against a simulated clock. Confirmed by search over the core crate:

```
$ grep -rnE 'tenant_id|tenantId|std::process|std::fs|std::net|reqwest|tokio|hyper|sqlite|rusqlite|libsql|SystemTime|Instant::now|chrono' kernel/relayflowd-core/src/
(none found)
```

The core crate's manifest carries only `jsonschema, serde, serde_json, sha2,
thiserror, ulid` — no I/O crates. The only clock is `SimClock`
(`kernel/relayflowd-core/src/clock.rs:10`, `Cell`-backed, asserts time cannot
move backwards). The `Journal` is a trait with an in-memory `MemoryJournal`
(`journal.rs:7`/`:24`); persistence lives in a **separate crate**
`kernel/relayflowd-journal`, and the socket server / `exec_det` / worker live in
the `kernel/relayflowd` binary. The three-crate split (pure core → journal →
I/O binary) is the language-boundary-enforces-architectural-boundary discipline
RFC §4 demands, and this PR's kernel change stays entirely inside the pure core.

**No product logic entered the kernel.** The kernel diff adds `cli` and
`triggers` to `RunSpec` and `cli` to the `Llm`/`Agent` step kinds, with comments
that are load-bearing and accurate: *"The kernel treats this as inert data;
`run.start` does not invoke the surface preflight in gate 1"* (spec.rs:34) and
*"Inert gate-1 declarations. Matching and dispatch belong to gate 2."*
(spec.rs:38). The kernel validates **shape** (empty cli, duplicate/invalid
triggers, unknown fields, cycles) and journals the spec as data in `run.spawned`;
it does not execute CLIs or triggers. This is the spec-as-data-at-the-boundary
pattern (settled decision #5; the sealed bundle includes "the flow's preflight
declaration," decision #14) — preflight is a surface step (`flows check`), the
kernel is the sealed-spec authority.

**No primitive was added — helpers only.** The closed kernel vocabulary is
exactly preserved. `StepType` stays `Deterministic | Llm | Agent`
(`spec.rs:270`); `EntryType` is untouched by this diff (the 13 RFC Appendix A
names: `run.spawned`, `step.attempt.started`, `step.completed`, `wait.event`,
`wait.human`, `sleep.until`, `wait.completed`, `stream.appended`,
`effect.recorded`, `effect.confirmed`, `epoch.summary`, `segment.closed`,
`run.completed` — `entry.rs:9`). `TriggerSpec` is a two-field data struct
(`spec.rs:336`), not a step type. Verification gates `exit_code` /
`output_contains` / `json_schema` are **authoring sugar** that compile
(`sdk/src/compile.ts:389` `toKernelVerification`) to the flat kernel gates
`{output_contains?, json_schema?}` — not new step verbs. No `type: integration`
anywhere (gate 6 honored):

```
$ grep -nE '^\+.*type: *integration|integration-primitive|slack-primitive|github-primitive' /tmp/pr-8.diff
(none — only doc lines stating none was added)
```

The SDK `toKernelStep` switch (`compile.ts:328`) is exactly the three rungs.
`docs/SURFACE.md:5` states the discipline: *"helpers make our primitives
effortless; plugins let the community extend the surface without ever touching
the kernel."* The SDK implements only the gate-1 minimal subset (compile +
validate + preflight + journal client), not the future `f.run`/`f.slack`/`f.memory`
surface — correct per AGENTS.md rule 6 (no speculative abstraction; the ladder
grows rung by rung).

**Fail-closed + `completionReason` discipline.** Spec parsing is fail-closed
everywhere: `deny_unknown_fields` on every non-flattened struct plus explicit
`reject_unknown_step_fields` for the `#[serde(flatten)]` steps (`spec.rs:154`),
pinned by `spec/tests.rs:31` (the typo-`output_contain` fail-open refutation) and
`:49` (the `verifcation` step-key refutation). Every completion carries a
reason: `StepCompletedPayload.completion_reason` (`entry.rs:182`),
`RunCompletedPayload.completion_reason` (`entry.rs:386`),
`WaitCompletedPayload.completion_reason` (`entry.rs:283`). The protocol is
fail-closed: a journal append that fails returns `journal_write_failed` and
fails the step (`sdk/src/protocol.ts:17`, `journal-client.ts:97` malformed
frame → `failAll`). The closed refusal taxonomy lives in
`sdk/src/failure-kinds.ts`.

**The journal protocol is the boundary, and nothing reaches around it.** The SDK
is a wire client (`sdk/src/journal-client.ts`) over a unix socket; it never
imports kernel internals. `run.start` accepts only the kernel-dialect spec
(`protocol.ts:70`), and the authoring `FlowSpec` never crosses the wire —
`JournalClient.runStart` converts via `toKernelSpec` first (documented at
`protocol.ts:72` and `journal-client.ts:163`).

**Small, single-purpose modules.** Submodules are split at the second-subject
boundary: `machine.rs` (420) delegates recovery to `machine/recovery.rs` (168);
`state.rs` (422) delegates budget math to `state/budget.rs` (43) and the pin
chain to `state/pins.rs` (142); `spec.rs` (452) separates its tests. No source
file carries two subjects. Tests pin deterministic kernel behavior
(`AGENTS.md` rule 5), including the crash/resume contract referenced by
`kernel/relayflowd/tests/crash_resume/` (outside this diff but part of the
gate).

## Summary

Structurally this is a clean gate-1 landing. The kernel change is inert data +
fail-closed shape validation inside the already-pure core crate; zero new step
or journal-entry vocabulary; no `type: integration`; the SDK is a protocol
client that compiles authoring sugar to the three kernel rungs. The two notes
(F1 test file 28 lines over the smell line; F2 validation-rule parity untested
across the boundary) are low-severity and non-blocking. No product logic in the
kernel, no primitive-where-a-helper-would-do, no file grown past its purpose
beyond the one test file noted.

REVIEW_PASSED
